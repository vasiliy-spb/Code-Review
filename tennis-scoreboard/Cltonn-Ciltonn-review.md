## Entity

### Player

<div align="right">

[Перейти к упоминанию в Match](#match) </div>

- ❗️Публичные сеттеры для всех полей класса:

  - Публичный сеттер для поля `id` позволяет изменять первичный ключ объекта, что может привести к полной рассинхронизации состояния сущности в приложении и её записи в базе данных.

  - Публичный сеттер для поля `name` позволяет произвольно менять имя игрока, которое должно быть его уникальным и неизменяемым свойством в рамках бизнес-логики.

Решение: удалить аннотацию `@Setter`. Инициализация полей должна происходить только один раз в момент создания объекта через конструктор.

- ❗️Аннотация `@NoArgsConstructor` без параметров создаёт `public` конструктор, позволяющий создавать невалидные объекты (без установки обязательных полей) в любом месте приложения. Hibernate достаточно конструктора без параметров с уровнем доступа protected — поэтому можно именно это значение установить в аннотации: `@NoArgsConstructor(access = AccessLevel.PROTECTED)`.

  Это предотвратит создание пустых, невалидных объектов из других частей приложения и будет сигналом другим разработчикам (потенциально), что этот конструктор предназначен в первую очередь для использования фреймворком, а не для прямого вызова в коде.

- ❗️Публичный конструктор без аргументов и сеттеры для каждого поля позволяют создавать игроков с заданным ID, а также изменять все поля после создания объекта или получения его из БД. Это нарушает инвариант "имя игрока должно быть неизменяемым после создания".

Вместо этого, для создания объекта JPA Entity внутри приложения, лучше создавать специальные конструкторы, которые принимают только поля, необходимые для создания валидного объекта (в данном случае, только `name`).

```java
public class Player {
    // ...

    public Player(String name) {
        this.name = name;
    }
    
    // ...
}
```

Также это сделает создание объектов более лаконичным:

```java
// сейчас так
Player player = new Player();
player.setName(name);

// будет так
Player player = new Player(name);
```

- Если имя поля совпадает с названием колонки, то параметр name в аннотации `@Column` можно опустить

```java
// сейчас так
@Column (name = "name", nullable = false, length = 30, unique = true)

// можно так
@Column (nullable = false, length = 30, unique = true)
```

### Match

- Пункты про:
  - ❗️Публичные сеттеры для всех полей класса (аннотация `@Setter` входит в `@Data`)
  - ❗️Публичный конструктор без аргументов
  - ❗️Конструктор с полями для создания валидного объекта

описанные в разделе [Player](#player), актуальны и для этого класса

- ❗️`@EqualsAndHashCode` (которая входит в `@Data`) обычно не используют в JPA сущностях. Конкретно здесь проблем быть не должно, но использование этих аннотаций вместе с `@Entity` не является хорошей практикой.

[**Использование @Data (Lombok) и @Entity (JPA) в одном классе**](#data-entity) <a id="back-from-data-entity"></a>

- ❗️Слово `MATCHES` (а также `MATCH`) является зарезервированным ключевым словом в некоторых диалектах SQL (например, для оператора `MATCH ... AGAINST` в полнотекстовом поиске). Хотя в конкретно в этом проекте проблем с этим не возникнет, не стоит использовать зарезервированные слова в качестве имён таблиц. Это может приводить к необходимости экранировать имя таблицы в нативных SQL-запросах или к синтаксическим ошибкам в некоторых СУБД.

[**Использование зарезервированных слов в качестве названий в БД**](#sql-keywords) <a id="back-from-sql-keywords"></a>

Лучше выбирать имена, которые гарантированно не конфликтуют с зарезервированными словами. Учитывая, что в таблице хранятся только завершённые матчи, можно выбрать более описательное и безопасное имя `FINISHED_MATCHES` или более общее `TENNIS_MATCHES`.

- Для создания ограничения на уровне таблицы используется аннотация `@Check` из пакета `org.hibernate.annotations`.

```java
import org.hibernate.annotations.Check;

@Entity
@Table (name = "matches")
@Check(constraints = "player1_id <> player2_id AND (winner_id = player1_id OR winner_id = player2_id)")
public class Match {
  // ...
}
```

Эта аннотация является устаревшей, начиная с 7-ой версии Hibernate

```java
@Target({TYPE, METHOD, FIELD})
@Retention(RUNTIME)
@Repeatable(Checks.class)
@Deprecated(since = "7")
public @interface Check {
	// ...
}
```

Использование устаревшего API создаёт технический долг. Такие аннотации могут быть удалены в будущих версиях Hibernate, что потребует переработки кода при обновлении зависимости.

На что заменить: использовать стандартный способ, предоставляемый JPA, через аннотацию `@Table`. Ещё можно добавить понятное имя для этого ограничения.

```java
@Entity
@Table(name = "matches",
        check = @CheckConstraint(name = "match_players_and_winner_check",
                constraint = "player1_id <> player2_id AND (winner_id = player1_id OR winner_id = player2_id)")
)
public class Match {
    // ...
}
```

Такой подход также улучшит переносимость — код не будет привязан к конкретной реализации JPA (`@Check` предоставляется Hibernate), что даёт гибкость в выборе технологий. Например, если в будущем проект решит сменить JPA-провайдера, данное ограничение продолжит работать, и код не придётся переписывать.

- Хорошим подходом будет оставить минимум необходимых аннотаций, достаточных для JPA Entity:

```java
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@Entity
@Table (name = "table_name", check = @CheckConstraint(name = "constraint_name", constraint = "[constraint conditions]"))
public class JpaEntity { 
    // ...
}
```

&#43; конструктор со всеми полями, кроме генерируемых автоматически (id), и equals/hashCode, реализованные на основе самостоятельно выбранных полей.

- Названия полей и колонок:

  - Поля для игроков названы `playerFirst` и `playerSecond`. `playerFirst` (существительное + прилагательное) менее идиоматично, чем `firstPlayer` (прилагательное + существительное). Поэтому лучше переименовать их в `firstPlayer` и `secondPlayer`.

  - В полях для игроков `playerFirst` и `playerSecond` — числительное написано словом, а в названиях колонок `"player1_id"` и `"player2_id"` — числительное написано цифрами.

Лучше переименовать поля для большего единообразия с именами колонок в БД.

Сейчас так:

```java
@JoinColumn (name = "player1_id", nullable = false, updatable = false)
private Player playerFirst;

@JoinColumn (name = "player2_id", nullable = false, updatable = false)
private Player playerSecond;
```

Лучше так:

```java
@ManyToOne
@JoinColumn (name = "first_player_id", nullable = false, updatable = false)
private Player firstPlayer;

@ManyToOne
@JoinColumn (name = "second_player_id", nullable = false, updatable = false)
private Player secondPlayer;
```

- Связи `@ManyToOne` не имеют явного указания о стратегии загрузки. По умолчанию для `@ManyToOne` используется `FetchType.EAGER`, что приводит к немедленной загрузке связанных сущностей при загрузке `Match`. Это может вызывать проблемы производительности (N+1 запросов) и излишнюю загрузку данных, особенно если связанные объекты не всегда нужны.

Как исправить: добавить `fetch = FetchType.LAZY` для каждого `@ManyToOne` поля. Также можно указать `optional = false` для явного обозначения обязательности связи (это может быть избыточно при `@JoinColumn(nullable = false)`, но улучшает читаемость).

```java
public class Match {
    
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "first_player_id", nullable = false, updatable = false)
    private Player firstPlayer;
    
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "second_player_id", nullable = false, updatable = false)
    private Player secondPlayer;
    
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "winner_id", nullable = false, updatable = false)
    private Player winner;
    
}
```

Это даст более тонкий контроль над тем, какие данные загружаются и в некоторых ситуациях оптимизирует загрузку и предотвратит проблемы с производительностью.

### TennisPoint

- Класс `TennisPoint` расположен в пакете `dto` (Data Transfer Object), но при этом содержит в себе бизнес-логику и относится к доменным моделям.

Пакет `dto` предназначен для классов, основная цель которых — передача данных между слоями приложения (например, между контроллером и сервисом, или от сервера к клиенту). Такие объекты должны быть простыми "контейнерами" данных, без сложного поведения.

`TennisPoint` является частью доменной модели — он описывает одно из понятий предметной области ("очко в гейме"). Размещение его в `dto` вводит в заблуждение и смешивает архитектурные слои.

Лучше переместить класс `TennisPoint` (и другие подобные классы, описывающие домен) в специальный пакет, например `domain` или `model`. Это сделает доменный слой независимым от других слоёв, а структуру проекта ясной и предсказуемой.

- Даже если сейчас у класса есть только final поля, то всё равно лучше использовать максимально "узкую" аннотацию `@RequiredArgsConstructor` вместо `@AllArgsConstructor`. Чтобы при добавлении новых non-final полей они автоматически не попадали в параметры конструктора.

- ❗️Константы `enum` используют числовые значения, которые не соответствуют правилам тенниса. В частности, `GAME(50)` и `ADVANTAGE(60)` отражают несуществующие в реальности 50 и 60 очков. Кроме того, `GAME` по своей сути является не "очком", а состоянием, завершающим гейм.

Это создаёт модель, которая не соответствует реальной предметной области. Использование "магических чисел" (50, 60) запутывает логику и заставляет писать код для их перевода в отображаемое значение (например, 60 -> "AD").

Смешение понятий "очки" (`FIFTEEN`) и "состояние" (`GAME`) в одном `enum` нарушает принцип единственной ответственности.

Как исправить:

  - Удалить константу `GAME`. Состояние "гейм выигран" должно отслеживаться на более высоком уровне (в классе, управляющем геймом).

  - Изменить тип `value` на `String` и хранить в нём реальное отображаемое значение очков.

Сейчас так:

```java
public enum TennisPoint {
    ZERO(0),
    FIFTEEN(15),
    THIRTY(30),
    FORTY(40),
    GAME(50),
    ADVANTAGE(60);

    private final int value;
}
```

Лучше так:

```java
public enum TennisPoint {
  ZERO("0"),
  FIFTEEN("15"),
  THIRTY("30"),
  FORTY("40"),
  ADVANTAGE("AD");

  private final String value;
}
```

Так `TennisPoint` станет точным и интуитивно понятным представлением очков в теннисе. Это упростит остальной код, так как отпадёт необходимость в преобразовании внутренних значений в отображаемые.

- Метод `getValuePoints()` дублирует информацию, которая должна храниться в поле `value` самого `enum`.

```java
public String getValuePoints() {
    switch (this) {
        case ZERO:
            return "0";
        case FIFTEEN:
            return "15";
        case THIRTY:
            return "30";
        case FORTY:
            return "40";
        case ADVANTAGE:
            return "AD";
        case GAME:
            return "GAME";
        default:
            return String.valueOf(value);
    }
}
```

Это нарушает принцип "Единого источника истины" ([**Принцип Single Source of Truth (SSOT)**](#ssot-principle) <a id="back-from-ssot-principle-to-tennispoint"></a>). Отображаемое значение очка определяется в двух местах: в поле `value` (для которого существует публичный геттер) и в `switch` внутри `getValuePoints`. Это создаёт риск рассинхронизации.

Как исправить: как было предложено в предыдущем пункте, нужно изменить тип поля `value` на `String` и хранить в нём строковые значения. Тогда этот метод превратится в простой геттер для поля `value`.

- Методы `getValuePoints()` и `getNextValuePoints()` можно переименовать:
  - `getValuePoints()` переименовать в `getDisplayName()`, `asString()` или `getDisplayValue()`.
  - `getNextValuePoints()` назвать просто `next()`.

Подбирать названия стоит так, чтобы назначение каждого метода было очевидно из его имени.

- В методе `getNextValuePoints()` используется устаревший `switch` оператор:

```java
public TennisPoint getNextValuePoints() {
    switch (this) {
        case ZERO:
            return FIFTEEN;
        case FIFTEEN:
            return THIRTY;
        case THIRTY:
            return FORTY;
        case FORTY:
            return GAME;
        default:
            return this;
    }
}
```

можно записать этот код в более современном `switch` выражении (доступном с Java 14):

```java
public TennisPoint getNextValuePoints() {
    return switch (this) {
        case ZERO -> FIFTEEN;
        case FIFTEEN -> THIRTY;
        case THIRTY -> FORTY;
        case FORTY -> GAME;
        default -> this;
    };
}
```

- ❗️Метод `getNextValuePoints()` не полностью отражает логику начисления очков в теннисе. Он не обрабатывает переход от `FORTY` к `ADVANTAGE`, а вместо этого возвращает `GAME`, а также на объекте `ADVANTAGE` возвращает `ADVANTAGE`. Такое поведение не соответствует названию метода и перекладывает лишнюю логику на вызывающий код.

Это нарушает Принцип инкапсуляции и [**Принцип наименьшего удивления (Principle of Least Astonishment, POLA)**](#pola) <a id="back-to-tennispoint-from-pola"></a>. Класс, который использует `TennisPoint`, ожидает, что вызов `getNextValuePoints()` вернёт следующее по порядку значение. Текущая реализация "молча" возвращает неверный результат в случаях `FORTY` и `ADVANTAGE`, перекладывая на внешний код логику для обработки этих ситуаций.

А также блок `default` просто возвращает текущее значение (`return this`), молча игнорируя необработанные случаи. "Тихое" поведение скрывает ошибки: если в `enum` будет добавлена новая константа, а `switch` не будет обновлён, программа не упадёт, а продолжит работать некорректно. Это усложняет отладку. Программа должна "падать быстро" (fail-fast) при обнаружении непредвиденного состояния.

Стоит изменить метод так, чтобы он соответствовал своей семантике "дать следующее очко".
  - При вызове на `FORTY` он должен возвращать `ADVANTAGE`.
  - При вызове на `ADVANTAGE` он должен выбрасывать исключение `IllegalStateException`, так как простого "следующего" очка не существует — это уже выигрыш гейма, что является особым состоянием, обрабатываемым на более высоком уровне.

```java
public TennisPoint next() {
    return switch (this) {
        case ZERO -> FIFTEEN;
        case FIFTEEN -> THIRTY;
        case THIRTY -> FORTY;
        case FORTY -> ADVANTAGE;
        case ADVANTAGE -> throw new IllegalStateException("Has not next value for ADVANTAGE");
    };
}
```

Так метод становится более предсказуемым — он возвращает корректное значение или явно сообщает об ошибке проектирования (попытка получить "следующее" очко после `ADVANTAGE`), а не молча возвращает некорректный результат.

- ❗️Метод `getValuePoints()`, предназначенный для преобразования значения перечисления в строку для отображения, напрямую вызывается из JSP (match-score.jsp). Такой подход нарушает [Принцип разделения ответственности (Separation of Concerns) в архитектуре MVC(S))](#soc-principle). <a id="back-from-soc-principle-to-tennispoint"></a>

Прямой вызов Java-методов из JSP создаёт сильную связь между слоем представления (View) и моделью данных (`TennisPoint`). Если в будущем потребуется изменить логику отображения очков (например, для локализации: "AD" -> "ПРЕИМ."), придётся изменять Java-код, что может затронуть другие части системы. В идеальной MVC-архитектуре изменение представления не должно требовать изменения модели.

Также код, логика которого разбросана между Java-классами и JSP-страницами, становится сложнее для понимания и сопровождения. Разработчику, работающему над JSP, нужно знать о существовании метода модели `getValuePoints()` и о том, как он работает. И наоборот, разработчик, изменяющий `TennisPoint`, должен помнить, что его метод используется напрямую в JSP, что создаёт неявные зависимости.

Решением будет не передавать во View доменные модели и, соответственно, не создавать в них методы, которые понадобились бы в JSP.

### MatchState

- Пункт про расположение доменной модели в пакете `dto`, описанный в разделе [TennisPoint](#tennispoint) <a id="forward-from-tennispoint-to-matchstate-1"></a>, актуален и для этого класса.

- ❗️Класс использует набор независимых `boolean` полей для представления состояния теннисного матча, многие из которых являются взаимоисключающими.

```java
public class MatchState {
    boolean matchOver = false;
    boolean tieBreak = false;
    boolean deuce = false;
    boolean player1Advantage = false;
    boolean player2Advantage = false;
}
```

Это ведёт к созданию хрупкой и трудно поддерживаемой системы:

  - Текущий дизайн позволяет создать объект, находящийся в логически невозможном состоянии. Например, `new MatchState(true, true, true, false, false)` — матч одновременно завершён, в нём идёт тай-брейк и счёт "ровно".

  - Отсутствие защиты инвариантов — объект не может гарантировать свою валидность. Ответственность за поддержание корректного состояния перекладывается на внешний код, который будет устанавливать эти флаги. Это приводит к размазыванию бизнес-логики и высокому риску ошибок.

 - Коду, который использует `MatchState`, придётся писать сложные `if-else` конструкции для анализа комбинаций флагов, вместо того чтобы просто проверить одно поле.

Как исправить:

Взаимоисключающие состояния — это классический случай для использования `enum`. Поэтому, если класс останется в приложении, следует превратить его в `enum` (возможно в несколько разных перечислений).

- ❗️Класс имеет аннотацию `@Setter`, что делает все его поля публично изменяемыми.

```java
@Setter
public class MatchState {
    // ...
}
```

Предоставление публичных сеттеров позволяет любой части приложения произвольно изменять состояние матча, обходя всю бизнес-логику. Можно установить флаг `matchOver = true` в середине первого гейма или задать `player1Advantage = true` и `player2Advantage = true` одновременно. Это нарушает инкапсуляцию и делает систему непредсказуемой и подверженной ошибкам.

Вторая проблема с инкапсуляцией в том, что все поля имеют модификатор доступа по умолчанию, что делает их доступными для любого класса в текущем пакете.

- Класс содержит данные, которые относятся (должны относиться) к разным доменным моделям (`deuce`, `player1Advantage`, `player2Advantage` — к гейму, `matchOver` — ко всему матчу, `tieBreak` — обозначает состояние гейма или особый тип гейма). Эта логика должна быть неотделима от соответствующих классов полноценных (богатых) доменных моделей. Вынесение её в другое место делает классы моделей более анемичными.

Лучшим решением будет провести декомпозицию предметной области и реализовать полноценные (богатые) классы доменных моделей, тогда данные из этого класса займут своё место в своих моделях и этот класс исчезнет.

- Имена полей (`tieBreak`, `deuce`, `player1Advantage`) не соответствуют общепринятой практике именования `boolean` свойств. В Java принято называть `boolean` переменные и методы доступа к ним так, чтобы они читались как вопрос, например `isFinished()` или `hasAdvantage()`. Имена `tieBreak` или `deuce` не отвечают на вопрос. Это делает код менее интуитивным для других разработчиков.

Если бы класс оставался с `boolean` флагами, поля следовало бы переименовать в `isTieBreak`, `isDeuce`, `hasPlayer1Advantage`.

### CurrentMatch

- Пункт про расположение доменной модели в пакете `dto`, описанный в разделе [TennisPoint](#tennispoint) <a id="forward-from-tennispoint-to-currentmatch-1"></a>, актуален и для этого класса.

- Класс содержит повторяющиеся поля для каждого из двух игроков: `sets1`/`sets2`, `games1`/`games2`, `points1`/`points2` и т.д. Это нарушение принципа DRY (Don't Repeat Yourself) и признак отсутствия важной абстракции в доменной модели.

> **DRY (Don't Repeat Yourself)** — принцип «Не повторяйся», направленный на снижение повторения кода и логики, так как изменения в повторяющихся участках требуют правок во многих местах, что увеличивает риск ошибок. Централизация логики делает код более поддерживаемым и надёжным.

Нет объекта, который бы отвечал за счёт одного игрока. Если потребуется добавить к счёту игрока новый атрибут (например, количество эйсов), придётся добавить два новых поля (`aces1`, `aces2`) и обновить всю логику, которая с ними работает. Это трудоёмко и чревато ошибками.

При разрастании класса, будет всё сложнее понять, какие поля относятся к игроку.

- ❗️`CurrentMatch` — это анемичная модель. Он представляет собой просто набор полей с геттерами и сеттерами, не содержащий никакой бизнес-логики.

Вся логика подсчёта очков, определения победителя и изменения состояния матча вынесена во внешние сервисные классы.

Почему это проблема:

  - Нарушение инкапсуляции: Любой внешний код может напрямую изменить любое поле объекта (`currentMatch.setGames1(10)`), полностью игнорируя правила тенниса. Это делает состояние объекта ненадёжным.

  - Процедурный стиль: Вместо того чтобы сказать объекту `currentMatch.awardPointTo(player1)`, внешний код "спрашивает" у него данные, обрабатывает их и записывает обратно. Это является антипаттерном в объектно-ориентированном программировании и порождает процедурный, а не объектно-ориентированный подход. Код превращается в набор процедур, которые оперируют над структурами данных, что лишает преимуществ ООП.

  - Сложность тестирования: Чтобы протестировать логику подсчёта очков, нужно тестировать сервисы, которые её содержат, что может потребовать мокирования зависимостей. Если бы логика была внутри доменного объекта, её можно было бы тестировать в полной изоляции.

- Имена полей вроде `sets1`, `games1` не очень информативны. Хотя в данном контексте понятно, что `1` относится к первому игроку, такой подход заставляет "расшифровывать" имена полей. Эта проблема решится автоматически при реализации богатых доменных моделей.

### PlayerRequest

- Можно переименовать `PlayerRequest` в `PlayerRequestDto`, чтобы о слое, к которому относится этот класс, сообщал последний суффикс — это будет лучше читаться.

- ❗️Класс имеет публичный конструктор без аргументов, сгенерированный аннотацией `@NoArgsConstructor`.

```java
@NoArgsConstructor
public class PlayerRequest {
  
    // ...
  
}
```

Объект `PlayerRequest` по своей сути должен содержать имя игрока. Конструктор без аргументов позволяет создать "пустой" экземпляр, у которого поле `name` будет `null`. Такой объект находится в невалидном состоянии. Если он будет передан дальше по цепочке вызовов без надлежащей проверки, это неизбежно приведёт к `NullPointerException`. Предоставление публичного конструктора без аргументов для такого объекта — это плохая практика, позволяющая создание невалидных данных.

Лучше удалить аннотацию `@NoArgsConstructor`. Класс должен создаваться только с теми данными, которые ему необходимы для валидного существования. В данном случае это `name`.

- `PlayerRequest` — это объект для передачи данных (DTO), который используется для получения имени игрока из HTTP-запроса. При отсутствии валидации создавать DTO из одной строки — избыточно, поэтому будет уместно добавить аннотации для валидации поля `name`.

DTO, представляющие входные данные (`Request`), — это первая линия защиты приложения. Отсутствие валидации означает, что в систему могут попасть некорректные данные:

  - `null`

  - Пустая строка (`""`)

  - Строка, состоящая только из пробелов (`"   "`)

  - Слишком длинное или слишком короткое имя

Это может привести к ошибкам `NullPointerException` на более глубоких слоях приложения, к записи некачественных данных в базу данных и к общему нестабильному поведению системы. Целостность данных должна обеспечиваться на всех уровнях, начиная с самого входа.

Можно добавить аннотации из пакета `jakarta.validation.constraints` для поля `name`. Как минимум, `@NotBlank` и `@Size` (пример в следующем пункте).

- ❗️Использование изменяемого DTO вместо неизменяемого. Аннотация `@Data` из Lombok генерирует публичные сеттеры. Это делает объект `PlayerRequest` изменяемым (mutable).

DTO, особенно объекты запросов, должны быть неизменяемыми (immutable) после их создания. Когда объект изменяем, его состояние может быть случайно или намеренно изменено после того, как он был создан. Это может привести к трудноуловимым багам, когда данные, прошедшие валидацию, позже меняются на невалидные перед их использованием.

Лучший способ сделать DTO неизменяемым — использовать Java Record. `record` — это специальный тип класса в Java, который по умолчанию является неизменяемым. Он автоматически генерирует `private final` поля, канонический конструктор, геттеры, `equals()`, `hashCode()` и `toString()`.

```java
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public record PlayerRequest(
    @NotBlank(message = "Player name cannot be blank.")
    @Size(min = 2, max = 30, message = "Player name must be between {min} and {max} characters.")
    String name
) {}
```

Также стоит удалить все аннотации над классом.

### CrudDao

- ❗️Интерфейс содержит метод `List<T> findAll()`, который подразумевает загрузку всех записей из таблицы без какой-либо фильтрации или ограничения (пагинации) за один запрос.

```java
public interface CrudDao <T, ID>{
    
    // ...
    
    List<T> findAll();
    
}
```

Наличие такого метода в общем CRUD-интерфейсе является архитектурным антипаттерном из-за:

  - Риска `OutOfMemoryError`: Для таблиц, которые могут содержать большое количество записей (например, история матчей за несколько лет), вызов этого метода приведёт к попытке загрузить все эти данные в оперативную память, что почти гарантированно вызовет ошибку `OutOfMemoryError` и падение приложения.

  - Плохой производительности: Даже если данных не так много, чтобы вызвать ошибку памяти, их загрузка может быть очень медленной и создавать ненужную нагрузку на базу данных и сеть.

  - Возможности для плохих практик: Разработчики, использующие этот DAO, могут пойти по пути наименьшего сопротивления и вызвать `findAll()`, для подсчёта общего количества матчей.

Для выборок данных лучше использовать методы с пагинацией, поэтому стоит удалить метод `findAll()` из общего интерфейса `CrudDao` или изменить его сигнатуру.

- Функционала, использующего методы `void delete(ID id)` и `Optional <T> update(T entity)` нет в текущей реализации, поэтому эти методы стоит удалить.

- ❗️В каждом методе DAO открывается и закрывается новая сессия Hibernate с помощью конструкции `try-with-resources`.

```java
@Override
public Optional<Player> findByName(String name) {
    try (Session session = HibernateUtil.getSessionFactory().openSession()) { // Новая сессия
        
        // ...
        
    } // Сессия закрывается
}

@Override
public Player save(Player player) {
    try (Session session = HibernateUtil.getSessionFactory().openSession()) { // Ещё одна новая сессия
        
        // ...
        
    } // Сессия закрывается
}
```

Это антипаттерн "Session-per-Operation" ("сессия на операцию"), который имеет два критических недостатка:

  - Низкая производительность: Создание объекта `Session` в Hibernate — это относительно "дорогая" операция. Она включает в себя получение соединения с базой данных из пула, инициализацию кэшей и тд. Создавать и уничтожать сессию при каждом вызове метода DAO неэффективно и создаёт лишнюю нагрузку.

 - Невозможность управления транзакциями: Самое главное — этот подход делает невозможным объединение нескольких операций DAO в одну бизнес-транзакцию. Например, если сервису нужно сохранить двух игроков, каждый вызов `playerDao.save()` будет выполнен в отдельной, независимой транзакции. Если второй вызов не удастся, первый уже будет закоммичен, что нарушает атомарность бизнес-операции и приводит к несогласованности данных.

Один из вариантов исправления — перейти на паттерн "Session-per-Request" ("сессия на запрос"). Его суть в том, что одна сессия Hibernate используется всеми сервисами и DAO на протяжении всей обработки HTTP-запроса.

- Текст HQL-запроса `"FROM Player p WHERE p.name = :name"` жёстко закодирован внутри метода `findByName`.

```java
@Override
public Optional<Player> findByName(String name) {
    try {
        Query<Player> query = session.createQuery("FROM Player p WHERE p.name = :name", Player.class);
        // ...
    }
    // ...
}
```

"Магические строки" в коде — источник ошибок. В них легко допустить опечатку, которую компилятор не сможет проверить. Также, если такой же запрос понадобится в другом месте, его придётся скопировать, что приведёт к дублированию. При изменении сущности придётся искать и исправлять все такие строки вручную.

Лучше вынести текст запроса в `private static final` константу и дать ей понятное имя.

```java
private static final String FIND_BY_NAME_HQL = """
        SELECT p
        FROM Player p
        WHERE p.name = :name
        """;
```

Когда запросы собраны в одном месте, их легко найти и изменить, а также снижается риск опечаток и исключается дублирование этой части кода.

- Для получения опционального результата используется `Optional.ofNullable(query.uniqueResult())`. Метод `uniqueResult()` возвращает `null`, если результат не найден и затем заворачивается в `Optional<T>`. В методе, который возвращает `Optional<T>` лучше использовать более идиоматичный метод `uniqueResultOptional()`, который сразу возвращает `Optional<T>`.

Сейчас так:

```java
public Optional<Player> findByName(String name) {
        
    // ...
        
    return Optional.ofNullable(query.uniqueResult());
}
```

Лучше так:

```java
public Optional<Player> findByName(String name) {
        
    // ...
        
    return query.uniqueResultOptional();
}
```

В текущей версии `hibernate-core` (`8.0.0.Alpha1`) оба метода помечены как deprecated, но эта версия ещё не является стабильной, а в последней стабильной версии (`7.2.5.Final` — на которую стоит перейти в проекте) использовать метод `uniqueResultOptional()` является хорошим подходом.

- Тело метода `findByName()` можно записать лаконичнее (цепочкой вызовов)

Сейчас так:

```java
@Override
public Optional<Player> findByName(String name) {
    try {
        Query<Player> query = session.createQuery("FROM Player p WHERE p.name = :name", Player.class);
        query.setParameter("name", name);
        return Optional.ofNullable(query.uniqueResult());
    } catch (Exception e) {
        // ...
    }
}
```

Можно так:

```java
@Override
public Optional<Player> findByName(String name) {
    try {
        return session.createQuery(FIND_BY_NAME_HQL, Player.class)
                .setParameter("name", name)
                .uniqueResultOptional();
    } catch (Exception e) {
        // ...
    }
}
```

API для построения запросов в Hibernate спроектирован как "текучий" (fluent), где каждый метод настройки возвращает сам объект, позволяя выстраивать вызовы в цепочку.

- ❗️В методах `findByName` и `findById` в блоке `catch (Exception e)` выбрасывается исключение `DatabaseOperationException` с сообщением, указывающим на то, что игрок не найден (`"Player not found by name/id in database"`).

```java
@Override
public Optional<Player> findByName(String name) {
    try {
        // ...
        return Optional.ofNullable(query.uniqueResult());
    } catch (Exception e) {
        // ...
        throw new DatabaseOperationException("Player not found by name in database");
    }
}

@Override
public Optional<Player> findById(Long id) {
    try {
        // ...
        return Optional.ofNullable(player);
    } catch (Exception e) {
        // ...
        throw new DatabaseOperationException("Player not found by id in database");
    }
}
```

Однако, если игрок действительно не найден, эти методы возвращают `Optional.empty()`. Блок `catch` выполняется только в случае возникновения ошибки при выполнении самой операции доступа к базе данных (например, проблемы с подключением, SQL-ошибка, ошибка Hibernate). Сообщение "игрок не найден" вводит в заблуждение относительно истинной причины сбоя.

Разработчик, столкнувшийся с `DatabaseOperationException` с таким сообщением, будет ошибочно полагать, что проблема в отсутствии данных, тогда как на самом деле произошёл сбой инфраструктурного характера (ошибка БД, сети). Это значительно затрудняет диагностику и увеличивает время на отладку.

Как исправить: Изменить текст сообщения в `DatabaseOperationException` таким образом, чтобы оно чётко указывало на проблему, возникшую при попытке выполнения операции доступа к БД, а не на отсутствие игрока.

```java
@Override
public Optional<Player> findByName(String name) {
    try {
        // ...
        return Optional.ofNullable(query.uniqueResult());
    } catch (Exception e) {
        // ...
        throw new DatabaseOperationException("Failed to retrieve player by name from database");
    }
}

@Override
public Optional<Player> findById(Long id) {
    try {
        // ...
        return Optional.ofNullable(player);
    } catch (Exception e) {
        // ...
        throw new DatabaseOperationException("Failed to retrieve player by ID from database");
    }
}
```

Это даст возможность быстрее и точнее определять истинную причину сбоя, различая случаи, когда объект не найден (возвращается `Optional.empty()`), от случаев, когда произошла техническая ошибка при обращении к базе данных. Обработка исключений станет более прозрачной и логичной.

- ❗️Во всех методах класса для обработки ошибок используется конструкция `catch (Exception e)`. Этот подход является антипаттерном, так как он перехватывает абсолютно все исключения, а не только те, которые связаны с операциями доступа к данным.

Блок `catch (Exception e)` перехватывает не только ожидаемые ошибки Hibernate (например, сбой подключения к БД), но и любые другие ошибки времени выполнения (`RuntimeException`), такие как `NullPointerException`, `IllegalArgumentException` или `ClassCastException`. Эти исключения почти всегда указывают на наличие бага в коде. Когда такой баг "ловится", он неверно классифицируется как ошибка базы данных и заворачивается в `DatabaseOperationException`. Это скрывает истинную причину проблемы и направляет разработчика по ложному следу при отладке.

Код, содержащий программную ошибку, должен "падать" как можно быстрее (Принцип Fail Fast) и с максимально понятным сообщением об ошибке (например, `NullPointerException` с точным указанием строки). Перехват `Exception` мешает этому, затягивая обнаружение и исправление дефектов.

Стоит заменить `catch (Exception e)` на перехват более специфичного исключения, которое является базовым для ошибок используемой технологии персистентности. Поскольку в проекте используется Hibernate, таким исключением является `org.hibernate.HibernateException`.

Вот так (пример для метода `save`):

```java
@Override
public Player save(Player player) {
    // ...
    try {
        // ...
    } catch (HibernateException e) {
        safeRollback(transaction, e);
        
        // Также лучше передать оригинальное исключение для сохранения stack trace (для этого надо реализовать соответствующий конструктов в DatabaseOperationException)
        throw new DatabaseOperationException("Failed to save player in database", e); 
    }
}
```

Это даст возможность чётко различать ошибки доступа к данным (которые будут перехвачены и обёрнуты в `DatabaseOperationException`) и программные баги (которые вызовут падение с оригинальным `RuntimeException`, указывая прямо на проблему в коде). Код становится более предсказуемым и устойчивым, так как его логика обработки ошибок сфокусирована исключительно на тех проблемах, для которых она предназначена — сбоях при работе с базой данных.

- ❗️Сейчас DAO управляет транзакциями самостоятельно:

```java
public Player save(Player player) {
    try (Session session = HibernateUtil.getSessionFactory().openSession()) {
        Transaction transaction = session.beginTransaction();
        try {
            // ...
            transaction.commit();
            // ...
        } catch (Exception e) {
            // ...
            transaction.rollback();
            // ...
        }
    }
}
```

Границы транзакции должны определяться бизнес-операцией, а не технической операцией доступа к данным. Бизнес-операция может включать в себя несколько вызовов DAO (например, сохранить игрока, а затем обновить матч). Все эти вызовы должны выполняться в рамках одной транзакции. Когда DAO сам управляет транзакцией, это становится невозможным. Ответственность за управление транзакциями должна лежать на сервисном слое, поэтому стоит перенести управление транзакциями именно в него.

Другой вариант — реализовать управление транзакциями в фильтре.

- ❗️Перед откатом транзакции в блоке catch в методе `save()` стоит добавить проверку, что она активна

```java
if (transaction != null && transaction.isActive()) {
    transaction.rollback();
}
```

иначе вызов `transaction.rollback()` может привести к исключению IllegalStateException.

- ❗Вызов `transaction.rollback()` стоит обернуть в try, иначе при возникновении исключения в этом методе оно замаскирует оригинальное исключение из основного блока try.

Например, так:

```java
public Player save(Player player) {
    Transaction transaction = null;
    try {
        transaction = session.beginTransaction();
        // ...
        transaction.commit();
    } catch (Exception e) {
        // ...
        safeRollback(transaction, e);
        throw new DatabaseOperationException("Failed to save player in database");
    }
}

private void safeRollback(Transaction transaction, Exception originalException) {
    if (transaction != null && transaction.isActive()) {
        try {
            transaction.rollback();
        } catch (Exception rollbackException) {
            originalException.addSuppressed(rollbackException);
        }
    }
}
```

- В методе `save` используется вложенный блок `try-catch` внутри конструкции `try-with-resources`. Такая структура является излишне сложной.

```java
@Override
public Player save(Player player) {
    try (Session session = HibernateUtil.getSessionFactory().openSession()) {
        Transaction transaction = session.beginTransaction();
        try {
            session.persist(player);
            transaction.commit();
            return player;
        } catch (Exception e) {
            log.error("Error saving player: {}", player.getName(), e);
            if (transaction != null) {
                transaction.rollback();
            }
            throw new DatabaseOperationException("Failed to save player in database");
        }
    }
}
```

Вложенная структура затрудняет чтение и понимание кода. Логика управления сессией (внешний `try`) и логика управления транзакцией (внутренний `try`) искусственно разделены, хотя по своей сути являются частью единой "единицы работы" (Unit of Work).

Стоит упростить структуру, используя один блок `try-catch` (`try-with-resources` не понадобится после перехода на `SessionFactory.getCurrentSession()`) для всей единицы работы.

```java
@Override
public Player save(Player player) {
    Session session = HibernateUtil.getSessionFactory().getCurrentSession();
    Transaction transaction = null;
    try {
        transaction = session.beginTransaction();
        
        session.persist(player);
        
        transaction.commit();
        return player;
    } catch (HibernateException e) {
        log.error("Error saving player: {}", player.getName(), e);
        safeRollback(transaction, e);
        throw new DatabaseOperationException("Failed to save player in database", e);
    }
}
```

Устранение лишней вложенности делает код более "плоским" и лёгким для восприятия.

- Методы `delete`, `update` и `findAll` нигде не используются в проекте.

"Мёртвый" код нарушает принцип YAGNI ("You Ain't Gonna Need It"). Он создаёт информационный шум, увеличивает объём кодовой базы, требует времени на поддержку и может вводить в заблуждение разработчиков, которые могут подумать, что эта функциональность используется.

Стоит удалить эти методы, а если они понадобятся в будущем, их всегда можно будет восстановить из системы контроля версий.

## service

- ❗️В пакете отсутствуют интерфейсы для сервисных классов. Все классы являются конкретными реализациями, от которых напрямую зависят другие компоненты приложения (например, сервлеты).

Почему это проблема:

  - Нарушение Принципа инверсии зависимостей (Dependency Inversion Principle): Принцип гласит, что модули верхних уровней не должны зависеть от модулей нижних уровней, а также они должны зависеть от абстракций. В данном случае вышестоящие модули (сервлеты) напрямую зависят от конкретных реализаций сервисов, что делает систему жёстко связанной и хрупкой.

  - Низкая тестируемость: Невозможно провести полноценное модульное тестирование компонентов, которые зависят от этих сервисов. Например, чтобы протестировать сервлет, использующий `MatchesService`, необходимо создавать полный экземпляр этого сервиса со всеми его реальными зависимостями (DAO, другие сервисы и тд), что превращает модульный тест в сложный интеграционный.

  - Низкая гибкость и невозможность расширения: Если потребуется создать альтернативную реализацию какого-либо сервиса, это потребует изменения кода во всех местах, где использовалась оригинальная реализация.

  - В классе-реализации публичные методы смешиваются с его внутренними или вспомогательными методами. Интерфейс же служит чётким, явным контрактом, который показывает, что сервис предоставляет внешнему миру, скрывая детали его внутренней работы.

Для каждого класса в этом пакете стоит создать интерфейс, который будет определять его публичный контракт, и изменить все зависимые классы так, чтобы они использовали этот интерфейс.

- ❗️Будет уместно реализовать управление транзакциями в слое сервисов, чтобы все обращения к БД в рамках одного запроса происходили в одной транзакции и предотвратить возможные race condition.

Это даст атомарность бизнес-операций: Вся бизнес-операция либо выполняется успешно целиком, либо полностью откатывается.

И будет способствовать целостности данных: Предотвращается попадание в базу данных неконсистентных, частично выполненных операций.

Чтобы избежать состояния гонки, можно инвертировать логику: сохранять, потом искать. Сначала оптимистично пытаться сохранить нового игрока. Если это не удаётся из-за нарушения уникальности, значит он уже был создан другим потоком и достаточно просто его найти.

```java
public Player findOrCreatePlayer(String playerName) {
    try {
        // "Оптимистично" пытаемся создать
        Player newPlayer = new Player(playerName);
        return playerDao.save(newPlayer);
    } catch (Exception e) {
        // Проверяем, что ошибка вызвана именно нарушением уникальности
        if (isConstraintViolation(e)) {
            // Если да, значит игрок уже есть — просто находим его
            // Вызов .get() здесь безопасен, так как мы уверены, что игрок существует
            return playerDao.findByName(playerName).get();
        }
        // Если причина в другом, то пробрасываем исключение
        throw e;
    }
}

// Проверяет, что ошибка вызвана именно нарушением уникальности
private boolean isConstraintViolation(Throwable e) {
    while (e != null) {
        if (e instanceof org.hibernate.exception.ConstraintViolationException) {
            return true;
        }
        e = e.getCause();
    }
    return false;
}
```

При таком подходе:

  - Соблюдается бизнес-требование и избегается состояние гонки. Приложение будет корректно работать при одновременных запросах на создание игроков.

  - Ошибка нарушения уникальности обрабатывается как штатная ситуация, а не как непредвиденный сбой.

  - Чуть улучшается производительность в "счастливом пути": Когда создаётся действительно новый игрок, выполняется всего один `INSERT` запрос вместо `SELECT` + `INSERT`.

Отсутствие единого, последовательного стиля именования затрудняет чтение кода. Разработчику приходится тратить дополнительное время и умственные усилия, чтобы убедиться, что `player1` и `playerOne` являются обозначениями одной и той же сущности. Это создаёт ненужную когнитивную нагрузку.

Также непоследовательное именование повышает риск случайных ошибок, особенно при копировании/вставке кода или при работе с большим количеством схожих переменных, когда легко перепутать один стиль с другим.

```java
public CurrentMatch createNewMatch(PlayerRequest firstPlayerRequest, PlayerRequest playerSecondRequest) {

    Player playerSecond = creatOrSavePlayer(playerSecondRequest);

}
```

Использование слов (например, `firstPlayer` и `secondPlayer`) даёт несколько преимуществ перед использованием цифр:

  - Эффективность работы в IDE: При вводе `first...`, IntelliJ IDEA однозначно предложит подсказку `firstPlayer`. При вводе `player...` IDE предложит оба варианта (`player1`, `player2`), что требует дополнительного действия для выбора нужного.

  - Удобство поиска: Искать по кодовой базе переменную тоже `firstPlayer` может быть проще, чем `player1` (по причине, из предыдущего пункта).

- ❗️Класс `NewMatchService` напрямую обращается к статическому полю `currentMatches` другого сервиса (`OngoingMatchService`).

```java
import static service.OngoingMatchService.currentMatches;

public class NewMatchService {
    // ...
    public CurrentMatch createNewMatch(PlayerRequest player1, PlayerRequest player2) {
        // ...
        currentMatches.put(matchId, currentNewMatch); // Прямая запись в чужое состояние
        return currentNewMatch;
    }
}
```

Почему это проблема:

  - Нарушение инкапсуляции: `NewMatchService` вторгается во внутреннее состояние `OngoingMatchService`. `OngoingMatchService` больше не контролирует своё состояние, и любой другой класс в проекте может так же напрямую изменить `Map` с матчами.

  - Нарушение принципа единственной ответственности (SRP): Ответственность за управление коллекцией текущих матчей должна быть исключительно внутри `OngoingMatchService`.

  - Скрытая зависимость и жёсткая связь: Зависимость от `OngoingMatchService` не объявлена в конструкторе, она скрыта за статическим импортом. Это делает код непредсказуемым и невозможным для понимания без анализа всех импортов. Сервисы становятся жёстко связанными друг с другом.

  - Статические поля — это, по сути, глобальные переменные. Они делают систему сложной для анализа, не потокобезопасной (если не использовать `ConcurrentHashMap`) и плохо тестируемой.

Как исправить:

  - Сделать поле `currentMatches` в `OngoingMatchService` нестатическим и приватным.

  - Создать в `OngoingMatchService` публичный метод для добавления нового матча.

  - Внедрить `OngoingMatchService` в `NewMatchService` через конструктор и вызывать его публичный метод.

- Метод `createNewMatch` выполняет как минимум две операции, которые затрагивают базу данных — `creatOrSavePlayer(player1)` и `creatOrSavePlayer(player2)`.

```java
public CurrentMatch createNewMatch(PlayerRequest player1, PlayerRequest player2) {
    Player playerOne = creatOrSavePlayer(player1); // Обращается к БД
    Player playerTwo = creatOrSavePlayer(player2); // Обращается к БД
    // ...
}
```

В текущей реализации эти вызовы не обёрнуты в единую транзакцию. Если создание первого игрока пройдёт успешно, а создание второго завершится с ошибкой (например, из-за временной недоступности БД), то система окажется в несогласованном состоянии: первый игрок будет создан, а матч — нет.

Вся логика создания нового матча должна выполняться в рамках одной транзакции. Если любая часть операции завершается неудачей, все изменения, сделанные внутри этой транзакции, должны быть отменены.

Самый простой способ это исправить (в этом проекте) — реализовать управление транзакциями в фильтре.

- Метод `createNewMatch` создаёт новый матч и возвращает полный объект `CurrentMatch`

```java
public CurrentMatch createNewMatch(PlayerRequest player1, PlayerRequest player2) {
    // ...
    return currentNewMatch;
}
```

хотя клиенту (вызывающему коду) достаточно знать только его идентификатор, чтобы затем обратиться к нему по другому эндпоинту. Поэтому возврат полного объекта `CurrentMatch` является избыточным. Более чистым решением был бы возврат `UUID`.

```java
public UUID createNewMatch(PlayerRequest player1, PlayerRequest player2) {
    // ...
    UUID matchId = ongoingMatchService.startNewMatch(player1, player2); // Создание матча делегировано соответствующему сервису
    return matchId;
}
```

Это сделает API сервиса более сфокусированным и минималистичным.

- ❗️Сервис "знает" слишком много о внутреннем устройстве `CurrentMatch`.

```java
CurrentMatch currentNewMatch = new CurrentMatch(matchId, playerOne.getId(), playerTwo.getId(), 0, 0, TennisPoint.ZERO, 0, 0, TennisPoint.ZERO, new MatchState());
```

Это следствие анемичной доменной модели. `NewMatchService` не должен знать, что начальный счёт — это `0, 0, TennisPoint.ZERO`. Эта логика должна быть инкапсулирована внутри самого доменного объекта `CurrentMatch` (или `OngoingMatch`). Доменный объект должен сам отвечать за своё начальное состояние.

Это исправится после реализации полноценных ("богатых") доменных моделей.

- Опечатка в имени метода: `creatOrSavePlayer` -> `createOrSavePlayer`.

- Метод `creatOrSavePlayer` используется только внутри этого класса, а также не должен являться частью публичного контракта `NewMatchService`, поэтому должен быть объявлен как `private`.

- В методе `creatOrSavePlayer` результат вызова `playerImpl.findByName(...).orElse(null)` присваивается переменной, которая затем проверяется на `null`.

```java
public Player creatOrSavePlayer(PlayerRequest playerRequest) { находиться в PlayerService ?
    Player player = playerImpl.findByName(playerRequest.getName()).orElse(null);
    if (player == null) {
        player = new Player();
        player.setName(playerRequest.getName());
        player = playerImpl.save(player);
    }
    return player;
}
```

Это лишает смысла использование `Optional`. `Optional` был введён в Java для того, чтобы избавиться от проверок на `null` и сделать код более выразительным и безопасным.

Как исправить: Использовать методы `Optional` для построения цепочки вызовов, избегая `null`.

```java
public Player findOrCreatePlayer(PlayerRequest playerRequest) {
    return playerImpl.findByName(playerRequest.getName())
        .orElseGet(() -> { // orElseGet выполнит код, только если Optional пуст
            Player newPlayer = new Player(playerRequest.getName());
            return playerImpl.save(newPlayer);
        });
}
```

Так код станет более лаконичным, безопасным (нигде не будет `null`) и будет соответствовать современным практикам.

- ❗️Метод `creatOrSavePlayer` использует подход "проверить, потом действовать": сначала он ищет игрока и, если не находит (`orElse(null)`), создаёт и сохраняет нового.

```java
public Player creatOrSavePlayer(PlayerRequest playerRequest) {
    Player player = playerImpl.findByName(playerRequest.getName()).orElse(null);
    if (player == null) {
        player = new Player();
        player.setName(playerRequest.getName());
        player = playerImpl.save(player);
    }
    return player;
}
```

Такая реализация не является потокобезопасной. Если два запроса одновременно пытаются создать матч с одним и тем же новым игроком, может возникнуть состояние гонки (race condition). Оба потока могут не найти игрока, и оба попытаются его сохранить, что приведёт к `ConstraintViolationException` от базы данных для второго потока. Приложение упадёт, хотя добавление матча с уже существующим игроком — часть нормального поведения.

Решение этой проблемы описано в разделе [PlayerService](#forward-from-newmatchservice-to-playerservice-1) <a id="forward-from-playerservice-to-newmatchservice-1"></a>

- Класса `NewMatchService` выполняет две задачи: находит или создаёт игроков (`creatOrSavePlayer`) и создаёт новый матч, помещая его в хранилище. Эти обязанности отобраны у других, более подходящих для их выполнения сервисов.

Это нарушает Принцип единственной ответственности (SRP) и создаёт запутанную архитектуру. Логика, связанная с игроками, оказывается в сервисе для создания матчей.

Лучшим решением будет ликвидировать `NewMatchService` и распределить его обязанности по существующим сервисам:

  - Логику поиска или создания игрока перенести в `PlayerService`.

  - Логику создания нового матча и добавления его в хранилище перенести в `OngoingMatchService`.

Так каждый сервис будет отвечать за свою, понятную часть бизнес-логики.

### OngoingMatchService

- ❗️Хранилище текущих матчей, `Map<UUID, CurrentMatch> currentMatches`, объявлено как публичная константа.

```java
public class OngoingMatchService {
    public static final Map<UUID, CurrentMatch> currentMatches = new ConcurrentHashMap<>();
    // ...
}
```

В таком виде поле `Map<UUID, CurrentMatch> currentMatches` является по сути глобальной переменной, что приводит к каскаду проблем:

  - Отсутствие инкапсуляции: Любой класс в приложении может получить прямой доступ к этой `Map` и делать с ней всё что угодно: очистить, удалить любой матч, заменить один матч другим и тд. `OngoingMatchService` никак не контролирует своё собственное состояние.

  - Весь код становится непредсказуемым. Чтобы понять, почему из `Map` пропал матч, придётся искать обращения к `OngoingMatchService.currentMatches` по всему проекту.

  - Невозможно написать изолированный юнит-тест для сервиса, который зависит от этого глобального состояния. Все тесты будут работать с одной и той же `static Map`, влияя друг на друга и приводя к непредсказуемым и "плавающим" результатам.

  - Жёсткая связь: Любой класс, использующий `import static ... currentMatches`, становится неявно и жёстко связан с `OngoingMatchService`, что делает архитектуру хрупкой.

Сам класс при таком дизайне перестаёт быть полноценным сервисом, а превращается в простой "держатель" для глобальной переменной.

Как исправить:

  - Сделать поле `currentMatches` приватным и нестатическим.
  - Сделать сам `OngoingMatchService` синглтоном де-факто (не обязательно реализовывать паттерн).
  - Предоставить публичные методы, которые инкапсулируют всю логику работы с `Map`.

- Метод `saveCurrentMatch` требует от вызывающего кода заранее сгенерировать `UUID` для нового матча и передать его в качестве ключа. Ответственность за генерацию уникального идентификатора должна лежать на самом хранилище (в данном случае, на `OngoingMatchService`), а не на клиенте этого сервиса. Клиент должен просто передать объект для сохранения (или DTO) и получить в ответ его идентификатор.

Лучше изменить метод создания матча так, чтобы он принимал только имена игроков (напрямую, в разных DTO или в одном DTO), сам создавал матч, генерировал для него `UUID`, сохранял матч в `Map` и возвращал сгенерированный `UUID`.

### MatchScoreCalculationService

> Многие пункты, относящиеся к этому классу, исправятся или потеряют смысл после проведения рефакторинга классов моделей и перехода к "богатой" доменной модели. Но так как многие рекомендации могут быть полезны и вне этого класса, они тоже будут описаны.

- ❗️Класс `MatchScoreCalculationService` содержит в себе всю бизнес-логику по подсчёту очков, геймов и сетов. Объекты, которыми он оперирует (`CurrentMatch`, `MatchState`), являются "анемичными" моделями — простыми контейнерами данных без собственного поведения. Сервис напрямую читает и записывает их поля.

Это главная архитектурная проблема этой части логики. По этим причинам:

  - Нарушение инкапсуляции: Данные (в `CurrentMatch`) и поведение (в `MatchScoreCalculationService`) полностью разделены. Любой другой сервис может так же напрямую изменить счёт матча, и объект `CurrentMatch` не сможет себя защитить.

  - Процедурный стиль: Вместо объектно-ориентированного подхода, где объекты сами управляют своим состоянием (и начисление очков происходит в духе `match.pointWonBy(player)`), получается процедурный код, который манипулирует внешними структурами данных.

  - Жёсткая связанность (Tight Coupling) и низкая связность (Low Cohesion): Сервис тесно связан с внутренним устройством `CurrentMatch` и `MatchState`. При этом логика, относящаяся к одному понятию (счёт), размазана по разным классам.

  - Сложность тестирования: Чтобы протестировать один конкретный сценарий (например, переход от "ровно" к "преимуществу"), нужно создать и настроить довольно громоздкий объект `CurrentMatch`, передать его в сервис и проверить, что все его поля были изменены правильно. Это сложно и хрупко.

Как исправить: Провести рефакторинг классов моделей с переходом к "богатой" доменной модели.

- Для внедрения зависимости `OngoingMatchService` используется конструктор, написанный вручную. Поскольку в проекте уже используется Lombok, этот шаблонный код можно сократить.

Если бы эта зависимость осталась нужна, стоило бы добавить аннотацию `@RequiredArgsConstructor` на уровне класса, тогда Lombok автоматически сгенерирует публичный конструктор для всех `final` полей.

- ❗️`MatchScoreCalculationService` (сервис для расчётов) зависит от `OngoingMatchService` (сервис для хранения текущих матчей). Это нарушает Принцип единственной ответственности. Задача этого сервиса — рассчитать новое состояние матча на основе старого. Ему не нужно знать, откуда это старое состояние пришло (из `Map`, из базы данных или было создано в тесте). Привязка к `OngoingMatchService` делает его cлабо переиспользуемым и усложняет тестирование.

Как исправить: Убрать зависимость от `OngoingMatchService`. Сервис должен принимать на вход объект `CurrentMatch` и возвращать его новое, обновлённое состояние. Оркестрация (например, получить старый матч -> рассчитать новый -> сохранить новый) должна быть вынесена на уровень выше.

- ❗️Логика в классе организована как сложная сеть вызовов приватных методов (`calculateScore` -> `countingGame` -> `checkGameWin` -> `checkSetWin` -> `checkMatchOver`).

```java
public CurrentMatch calculateScore(UUID uuid, Long playerId) {
    CurrentMatch currentMatch = ongoingMatchService.getCurrentMatch(uuid);
    MatchState state = currentMatch.getMatchState();
    if (!state.isMatchOver()) {
        if (!state.isTieBreak()) {
            if (state.isDeuce()) {
                countingDeuce(currentMatch, playerId);
            } else if (state.isPlayer1Advantage() || state.isPlayer2Advantage()) {
                countingAdvantage(currentMatch, playerId);
            } else {
                countingGame(currentMatch, playerId); // к этой строке уже сложно чётко сформулировать при каких конкретно условиях она выполняется
            }
        } else {
            countingTieBreak(currentMatch, playerId);
        }
        checkMatchOver(currentMatch);
    }

    return currentMatch;
}
```

В такой структуре становится сложно отследить полный путь выполнения для одного выигранного очка. Чтобы понять или отладить код, разработчику нужно держать в голове всю цепочку вызовов и мысленно отслеживать, как мутирует объект `CurrentMatch` в каждом из методов. Добавление нового правила (например, какого-нибудь особенного сета) потребует изменений во многих местах этой запутанной структуры.

Как исправить: Провести рефакторинг классов моделей с переходом к "богатой" доменной модели.

- ❗️Все `private` методы (`countingGame`, `checkDeuce` и тд) принимают в качестве параметра объект `CurrentMatch` и напрямую изменяют его поля. Это модификация через побочные эффекты (side effects).

Методы с побочными эффектами непредсказуемы. При чтении кода `countingGame(currentMatch, playerId)` невозможно понять, что именно произойдёт с объектом `currentMatch` внутри метода, не изучив его реализацию. Это усложняет отладку, так как любой метод может изменить общее состояние в самый неожиданный момент.

В общем случае это исправляется через функциональный подход: вместо изменения существующего объекта возвращать его новую, изменённую копию. Но в этом проекте проблема исчезнет сама после рефакторинга доменных моделей.

- Методы `calculateScore` и `checkGameWin` содержат глубокую вложенность `if-else` конструкций, достигающую 3-х уровней.

```java
public CurrentMatch calculateScore(UUID uuid, Long playerId) {
    CurrentMatch currentMatch = ongoingMatchService.getCurrentMatch(uuid);
    MatchState state = currentMatch.getMatchState();
    if (!state.isMatchOver()) {
        if (!state.isTieBreak()) {

            } else {
                countingGame(currentMatch, playerId);
            }
        } else {
            countingTieBreak(currentMatch, playerId);
        }
        checkMatchOver(currentMatch);
    }

    return currentMatch;
}

            }
```

- ❗️Блок `if-else`, определяющий победителя сета после тай-брейка, построен так, что если первый игрок не выиграл, то победа автоматически присуждается второму.

```java

        currentMatch.setSets1(currentMatch.getSets1() + 1); // Если счёт первого больше счёта второго
    } else { 
        currentMatch.setSets2(currentMatch.getSets2() + 1); // Если счёт второго больше ИЛИ РАВЕН счёту первого 
    }
    // ...
}
```

Такая логика является неявной и потенциально небезопасной. Она корректно работает только потому, что внешнее условие (`Math.abs(...) >= MIN_POINT_DIFFERENCE`) отсекает случай равенства очков. Однако если по какой-то причине в этом внешнем условии будет ошибка, и метод `checkTieBreakOver` вызовется при равном счёте (например, 7-7), победа в сете будет ошибочно присуждена второму игроку.

Код должен быть написан так, чтобы его намерения были очевидны, а поведение — предсказуемо даже в случае непредвиденных обстоятельств. Поэтому лучше использовать более явную конструкцию `if-else if`, которая чётко разделяет случаи победы первого и второго игрока.

```java
private void checkTieBreakOver(CurrentMatch currentMatch) {
    // ...
    if (currentMatch.getGames1() > currentMatch.getGames2()) {
        currentMatch.setSets1(currentMatch.getSets1() + 1);
    } else if (currentMatch.getGames1() < currentMatch.getGames2()) { 
        currentMatch.setSets2(currentMatch.getSets2() + 1);
    }
    // ...
}
```

- ❗️В методе `countingTieBreak` очки в тай-брейке засчитываются как выигранные геймы:

```java

        currentMatch.setGames1(currentMatch.getGames1() + 1); // очки тай-брейка засчитываются как геймы

        currentMatch.setGames2(currentMatch.getGames2() + 1); // очки тай-брейка засчитываются как геймы

    checkTieBreakOver(currentMatch);
}
```

это не соответствует правилам тенниса. Хотя тип полей `games1` и `games2` и подходит для хранения счёта тай-брейка, они отвечают за другой уровень теннисного матча и поэтому не должны использоваться для других целей.

Для хранения счёта тай-брейка (только в контексте текущей реализации) должны были бы существовать отдельные, специально предназначенные для этого поля.

При реализации богатых доменных моделей, правильным подходом будет выделить тай-брейк в отдельную абстракцию.

Это маскирует ошибки. Если матч во внутреннем хранилище был найден, но произошла ошибка при сохранении в базу данных, вызывающий код получит ложное сообщение "матч не найден". Это делает отладку практически невозможной. Причина сбоя теряется.

Стоит обрабатывать разные типы ошибок по-разному:

  - Если матч не найден в `OngoingMatchService`, нужно выбрасывать `NotFoundException`.

  - Если происходит ошибка при работе с базой данных, нужно пробрасывать дальше специфичное исключение, например, `DatabaseOperationException`.

  - `orElseThrow()` должен вызываться с созданием осмысленного исключения.

- Класс содержит приватный метод `getWinner`, который заново вычисляет, кто победил в матче, анализируя счёт по сетам.

```java
private Player getWinner(CurrentMatch currentMatch) {
    Player playerWinner;
    int setsPlayer1 = currentMatch.getSets1();
    int setsPlayer2 = currentMatch.getSets2();
    if (currentMatch.getMatchState().isMatchOver()) {
        if (setsPlayer1 > setsPlayer2) {
            playerWinner = playerImpl.findById(currentMatch.getIdPlayer1()).orElseThrow();
            return playerWinner;
        } else if (setsPlayer2 > setsPlayer1) {
            playerWinner = playerImpl.findById(currentMatch.getIdPlayer2()).orElseThrow();
            return playerWinner;
        }
    }
    throw new IllegalStateException("Match is't finished");
}
```

Это нарушение Принципа единственной ответственности (SRP). Определение победителя — это задача логики подсчёта очков, которая могла (в текущей реализации) быть в `MatchScoreCalculationService`, а в идеале — инкапсулирована в "богатой" доменной модели.

Этот сервис не должен заниматься перепроверкой или вычислением результатов. Он должен получать на вход уже полностью готовые данные и просто сохранять их.

Стоит убрать метод `getWinner`. `CurrentMatch` или другой объект, описывающий состояние завершающегося матча, должен уже содержать ID (или имя) победителя, определённый на предыдущем шаге.

Сервисный слой должен служить границей между доменной моделью и слоем контроллеров. Передача объектов JPA-Entity наружу смешивает слои и является антипаттерном ("протекающая абстракция").

  - Если JSP-страница попытается получить доступ к лениво загружаемому полю `Match` (например, к `match.getFirstPlayer().getName()`), произойдёт ошибка, так как сессия Hibernate к этому моменту уже будет закрыта.

Как исправить:

Сервис должен возвращать DTO, специально созданный для этой задачи (например, `PagedResponseDto`, содержащий и список DTO-матчей, и мета-информацию). Вся логика преобразования из `Entity` в DTO должна быть инкапсулирована в маппере.

Это сделает сервис более соответствующим принципу разделения слоёв, исключит `LazyInitializationException` и утекание внутренних данных (которые могут содержаться в JPA-Entity) наружу.

- ❗️При поиске по имени игрока метод `getMatches` сначала выполняет один запрос к БД, чтобы найти игрока и получить его `ID`, а затем выполняет второй запрос, чтобы найти матчи по этому `ID`.

```java
public List<Match> getMatches(String playerName, int page, int pageSize) {

    Optional<Player> playerForFind = player.findByName(playerName); // Первый запрос
    // ...
    Long playerId = playerForFind.get().getId();
    return match.findAllByPlayerNameWithPagination(playerId, page, pageSize); // Второй запрос
}
```

Это лишний запрос к базе данных. Лишние запросы к БД увеличивают задержку и нагрузку на систему. Получение матчей стоит выполнять одним запросом, который сразу соединяет таблицы матчей и игроков и фильтрует по имени игрока. Эта проблема вызвана, в том числе, и неверным дизайном `MatchImpl`, который принимает `playerId`, а не `playerName` и должна исчезнуть после исправления слоя DAO.

- ❗️Сервис предоставляет два метода: `getMatches(String playerName, ...)` и `getTotalMatchesCount()`. Метод для подсчёта общего количества записей не принимает фильтр по имени игрока.

Это приводило бы к ошибке в пагинации (если бы работал фильтр по имени игрока):

  - Пользователь ищет матчи игрока `"Player 1"`.

  - Сервис вызывает `getMatches("Player 1", ...)` и получает, например, 15 матчей.

  - Для отрисовки пагинации сервлет вызывает `getTotalMatchesCount()`, который возвращает общее количество всех матчей в базе, например, 150.

  - Пользователь видит "найдено 15 матчей. Страница 1 из 10", что является логической ошибкой.

Сервис должен иметь два метода для подсчёта: один для общего количества, другой для отфильтрованного. И вызывать правильный метод в зависимости от наличия фильтра.

- ❗️`MatchesService` напрямую зависит от `PlayerImpl` (DAO-слоя игрока), хотя в приложении уже существует `PlayerService`, который должен инкапсулировать всю логику работы с игроками.

`MatchesService` вынужден знать о деталях получения данных об игроках, дублируя логику, которая должна быть скрыта внутри `PlayerService`.

Сервисы должны, по возможности, взаимодействовать друг с другом, а не "перепрыгивать" через уровень абстракции и обращаться напрямую к DAO других доменных областей.

Если в проекте останется `PlayerService`, стоит заменить прямую зависимость от `PlayerCrud` на зависимость от `PlayerService`.

- Метод `getMatches` содержит суффикс `Matches`, который дублирует контекст, уже заданный названием класса `MatchesService` и дополнительно понятный из типа возвращаемого значения. Можно переименовать метод просто в `get` или в `getPaginated` (получить с пагинацией).

Также можно переименовать метод `getTotalMatchesCount` в `getTotalCount`.

- Проверка `if (playerName == null)` не учитывает случаи, когда `playerName` является пустой строкой (`""`) или строкой, состоящей только из пробельных символов.

```java
public List<Match> getPaginated(String playerName, int page, int pageSize) {
    if (playerName == null) {
        return match.findAllWithPagination(page, pageSize);
    }
    // ...
}
```

Для пользователя передача пустого имени и отсутствие имени — это, по сути, одно и то же действие (отсутствие фильтрации). Однако текущая логика обрабатывает эти случаи по-разному. При передаче пустой строки код попытается найти в базе данных игрока с пустым именем, что возвращает пустой результат.

Вместе с проверкой на `null` лучше дополнительно использовать метод `String.isBlank()`, который проверяет строку на пустоту и наличие только пробельных символов.

```java
public List<Match> getPaginated(String playerName, int page, int pageSize) {
    if (playerName == null || playerName.isBlank()) {
        return match.findAllWithPagination(page, pageSize);
    }
    // ...
}
```

Так при пустом фильтре будут видны все матчи и поведение приложения станет более предсказуемым для конечного пользователя.

- Если при фильтре по имени игрока не найдено ни одного матча можно возвращать неизменяемый список.

Сейчас так:

```java
if (playerForFind.isEmpty()) {
    return new ArrayList<>();
}
```

Лучше так:

```java
if (playerForFind.isEmpty()) {
    return Collections.emptyList();
}
```

Это будет дополнительной гарантией того, что он не будет ошибочно изменён на пути во View.

- Зависимость `NewMatchService` извлекается из `ServletContext` по жёстко закодированной строке `"newMatchService"`.

Сейчас так:

Такой подход не защищён от опечаток и затрудняет рефакторинг. Если имя класса или ключ изменятся, связь между слушателем контекста (где зависимость устанавливается) и сервлетом (где она извлекается) будет нарушена, что приведёт к `NullPointerException` во время выполнения.

```java
@Override
public void init() throws ServletException {
```

Это создаст более строгую и безопасную связь.

- Имена игроков извлекаются из запроса, упаковываются в два отдельных объекта `PlayerRequest` и валидируются по одному. Затем выполняется третья, отдельная проверка для сравнения имён.

```java
@Override
protected void doPost(HttpServletRequest request, HttpServletResponse response) throws IOException, ServletException {
    String playerOne = request.getParameter("playerOne");
    String playerTwo = request.getParameter("playerTwo");
    try {
        
        // создаётся DTO для первого игрока
        PlayerRequest playerRequest1 = new PlayerRequest();
        playerRequest1.setName(playerOne);

        // валидируется DTO для первого игрока
        ValidationUtil.validate(playerRequest1);

        // создаётся DTO для второго игрока
        PlayerRequest playerRequest2 = new PlayerRequest();
        playerRequest2.setName(playerTwo);

        // валидируется DTO для второго игрока
        ValidationUtil.validate(playerRequest2);
        
        
        // валидируются оба DTO
        ValidationUtil.validatePlayers(playerRequest1, playerRequest2);

        // ...
    } catch (...) {
        // ...
    }
}
```

Код получается многословным и повторяющимся. Создаётся несколько отдельных объектов там, где можно было бы обойтись одним, инкапсулирующим весь запрос.

Вместо этого можно создать единый DTO для запроса на новый матч и делегировать всю логику валидации валидатору:

```java
// Создаём DTO для запроса
public record NewMatchRequestDto(
        String firstPlayerName, 
        String secondPlayerName 
) {}

// Упрощаем сервлет
protected void doPost(HttpServletRequest request, HttpServletResponse response) {
    String firstPlayerName = request.getParameter("firstPlayer");
    String secondPlayerName = request.getParameter("secondPlayer");
    
    NewMatchRequestDto newMatchRequestDto = new NewMatchRequestDto(firstPlayerName, secondPlayerName); // Создаём только один объект
    validator.validate(newMatchRequestDto); // Один вызов валидатора для всех проверок
    
    // ... 
}
```

Так вся логика валидации инкапсулируется в валидаторе, а код сервлета становится чище и короче.

- ❗️После валидации `PlayerRequest`, сервлет получает доменную модель матча (`CurrentMatch`) из `NewMatchService` только для того, чтобы извлечь из него ID.

```java
@Override
protected void doPost(HttpServletRequest request, HttpServletResponse response) throws IOException, ServletException {
    // ...
        
    CurrentMatch match = newMatchService.createNewMatch(playerRequest1, playerRequest2);

    UUID match_id = match.getMatchId();

    // ...
}
```

Это нарушает границы между слоями приложения. Сервлет не должен работать с доменными моделями и не должен знать об их внутреннем устройстве — ему это не нужно для выполнения его задачи. Такая связь делает систему жёсткой: изменение в `CurrentMatch` может сломать сервлет.

Сервисный слой должен возвращать только те данные, которые необходимы контроллеру. В данном случае, сервлету нужен только ID созданного матча для редиректа.

- В методе `doPost` имя переменной `match_id` написано в стиле `snake_case`, что не соответствует соглашениям по написанию кода на Java. В Java принято использовать `camelCase` для имён переменных, параметров и методов. Нарушение этой конвенции делает код менее читаемым для Java-разработчиков и выбивается из общего стиля.

Стоит переименовать переменную в стиле `camelCase`.

- Обработка `InvalidParameterException` находится в блоке `try-catch` внутри метода `doPost`.

```java
catch (InvalidParameterException e) {
    request.setAttribute("error", e.getMessage());
    request.getRequestDispatcher("/new-match.jsp").forward(request, response);
}
```

Если подобная валидация понадобится в других сервлетах, эту логику придётся дублировать, что нарушит принцип DRY (Don't Repeat Yourself).

Можно создать фильтр, который будет оборачивать все запросы и централизованно обрабатывать все исключения.

- Строковые литералы (например, `"playerOne"`, `"playerTwo"`, `"error"`, `"new-match.jsp"` и др), которые используются в качестве ключей для атрибутов и параметров, а также для указания путей, лучше вынести в константы с понятными именами. Именованная константа делает код более семантически понятным.

- Параметры запроса и переменные для них используют числительные прописью (`"playerOne"`, `"playerTwo"`), а объекты `PlayerRequest` — цифрами (`playerRequest1`, `playerRequest2`). Пункт о последовательном именовании, описанный в разделе [NewMatchService](#newmatchservice), актуален и в этом случае. <a id="back-from-newmatchservice-to-newmatchservlet-1"></a>

[**Архитектурный антипаттерн: "Толстый контроллер" (Fat Controller)**](#fat-controller) <a id="back-from-fat-controller"></a>

Сервлет должен быть "тонким контроллером", делегирующим всю бизнес-логику одному фасадному сервису.

Как исправить: Создать один сервис, который инкапсулирует всю логику, связанную с ходом матча, и скрыть за ним работу других сервисов и слоёв.

Это нарушает [Принцип разделения ответственности (Separation of Concerns)](#soc-principle) <a id="back-from-soc-principle-to-matchscoreservlet"></a>

Сервлет не должен иметь доступа к слою доступа к данным — это создаёт жёсткую связь и смешивает ответственности. Вся работа с данными должна происходить внутри сервисного слоя.

- ❗️В классе есть несколько проблем с обработкой ошибок:

  - В методе `doGet` при отсутствии параметра `uuid` выбрасывается `NotFoundException`, что семантически неверно.

  ```java
  if(matchId==null) {
      throw new NotFoundException("Match ID not found");
  }
  ```

  Отсутствие обязательного параметра — это ошибка клиента (Bad Request, 400), а не ошибка "не найдено" (Not Found, 404) или серверная ошибка (500).

  Стоит заменить `NotFoundException` на `InvalidParameterException` при отсутствии `uuid`.

  - Вызов `UUID.fromString(matchId)` может выбросить `IllegalArgumentException`, если `matchId` имеет неверный формат.

  ```java
  UUID uuid = UUID.fromString(matchId);
  ```

  Это исключение не обрабатывается и приведёт к ошибке 500 (Internal Server Error).

  Стоит обернуть парсинг UUID в `try-catch` и выбрасывать специализированное исключение `InvalidParameterException`.

  - Вызов `orElseThrow()` без аргументов в методе `setAttribute` может выбрасывать стандартное `NoSuchElementException`, которое не несёт бизнес-смысла и также приводит к ошибке 500.

  ```java
  public void setAttribute(HttpServletRequest request, CurrentMatch match) {
      Player player1 = playerImpl.findById(match.getIdPlayer1())
              .orElseThrow();
      Player player2 = playerImpl.findById(match.getIdPlayer2())
              .orElseThrow();
      // ...
  }
  ```

  Этот код должен исчезнуть из сервлета, но в подобных случаях вместо `orElseThrow()` лучше использовать `orElseThrow(Supplier<? extends X> exceptionSupplier)` с созданием специфического исключения.

Неправильная обработка ошибок вводит в заблуждение клиента API (браузер) и разработчиков. Ошибки 500 должны сигнализировать о проблемах на сервере, а ошибки формата данных или отсутствия параметров (4xx) — о проблемах в запросе клиента.

- ❗️Логика определения завершения матча и вычисления победителя находится прямо в методе `doPost`.


Это нарушение принципа разделения ответственности и признак "толстого" контроллера. Сервлет не должен содержать бизнес-правил. Это затрудняет переиспользование логики, её тестирование и поддержку.

Стоит перенести всю эту логику в соответствующий сервисный слой.

- ❗️Контроллер передаёт в слой представления доменные модели (через `MatchResultView resultView`).

Как исправить: Удалить ручное создание сервиса и получать его напрямую из `ServletContext`.

- ❗Сервлет передаёт в слой представления JPA сущности (`List<Match> matches`).

## util

### ValidationUtil

- Класс назван `ValidationUtil`. Суффикс `Util` часто подразумевает, что класс является сборником разнородных статических методов без чёткой единой ответственности. Сейчас класс занимается исключительно валидацией, связанной с игроком, поэтому можно использовать более специфичное имя `PlayerNameValidator`.

- В методе `validate` жёстко закодированы числовые значения для минимальной и максимальной длины имени (2 и 30).

```java
if (playerName.length() < 2 || playerName.length() > 30) {
    throw new InvalidParameterException("Player name cannot be less 2 characters and more 30 characters");
}
```

Если требования к длине имени изменятся, придётся вносить правки как минимум в двух местах: в логическом условии и в строке с сообщением об ошибке. Это повышает риск рассинхронизации.

Значения захрдкоженных чисел 2 и 30 понятны сейчас, когда правил валидации мало, но когда их станет больше, то держать весь контекст в уме станет сложнее.

Стоит вынести "магические числа" в `private static final` константы и использовать их для формирования и логики, и сообщения об ошибке.

```java
public final class PlayerNameValidator {
  private static final int MIN_NAME_LENGTH = 2;
  private static final int MAX_NAME_LENGTH = 30;
  // ...

  public static void validate(PlayerRequest playerRequest) {
      // ...
      if (playerName.length() < MIN_NAME_LENGTH || playerName.length() > MAX_NAME_LENGTH) {
          throw new InvalidParameterException(
              String.format("Player name must be between %d and %d characters.", MIN_NAME_LENGTH, MAX_NAME_LENGTH)
          );
      }
      // ...
  }
}
```

- ❗️Сообщение об ошибке, которое видит пользователь при несовпадении с регулярным выражением, является неполным и вводит в заблуждение.

```java
if(!NAME_PATTERN.matcher(playerName).matches()) {
    throw new InvalidParameterException("Use only English or Russian letters");
}
```

Регулярное выражение `^[a-zA-Zа-яА-ЯёЁ\s\-'.]+$` разрешает не только буквы, но и пробелы, дефисы, апострофы и точки. Текущее сообщение об ошибке умалчивает об этом. Пользователь, который введёт корректное имя `"John O'Doe"`, будет сбит с толку сообщением "Используйте только буквы".

Как исправить: Сделать сообщение об ошибке максимально точным и полным, перечислив в нём все разрешённые типы символов.

```java
if (!NAME_PATTERN.matcher(playerName).matches()) {
  throw new InvalidParameterException(
      "The name contains invalid characters. Allowed characters include: English or Russian letters, spaces, hyphens, apostrophes, and dots."
  );
}
```

Это улучшит пользовательский опыт при работе с системой — чёткие и точные сообщения об ошибках помогают быстрее исправлять свой ввод.

- Сейчас регулярное выражение `"^[a-zA-Zа-яА-ЯёЁ\\s\\-'.]+$"` пропускает бессмысленные строки, такие как `'---'` или смешанные языки — `Игорь Petrov` (смесь латиницы и кириллицы). Это приводит к "загрязнению" базы данных некачественными данными.

Стоит добавить в метод `validate` дополнительные проверки после прохождения регулярного выражения. Например, запретить имена, которые меньше чем наполовину состоят из букв или используют разные языки.

- Непоследовательная логика валидации: Метод `validate` проверяет длину и паттерн на "сырой" строке, полученной из `getName()`. А метод `validatePlayers` вызывает `getName().trim()` перед сравнением.

Это означает, что имя, дополненное пробелами до подходящей длины (например, `"a      "`), пройдёт проверку в `validate`.

Проверка длины тоже должна применяться к уже "очищенной" строке.

### HibernateUtil

- ❗️В текущей реализации отсутствует метод для закрытия `SessionFactory` при остановке приложения. `SessionFactory` владеет важными ресурсами, включая пул соединений с базой данных. Если эти ресурсы не освободить корректно, это может привести к утечкам памяти и проблемам с подключением к БД, особенно в окружениях, которые не управляют жизненным циклом приложения автоматически (к ним онтностися и Tomcat).

Стоит добавить статический метод `shutdown()`, который будет закрывать `SessionFactory` и вызывать его при завершении работы приложения (например, в `contextDestroyed` из `AppContextListener`). Такой подход гарантирует, что все ресурсы, удерживаемые Hibernate, будут освобождены при остановке приложения и предотвращает потенциальные утечки и ошибки, связанные с "висячими" соединениями.

```java
public static void shutdown() {
    if (sessionFactory != null) {
        sessionFactory.close();
    }
}
```

- В блоке `catch`, отвечающем за обработку ошибок инициализации, присутствует комментарий `//TODO`.

```java

```

`TODO` комментарии — это маркеры незавершённой работы и технического долга. Перед деплоем приложения стоит убедиться, что все запланированные задачи выполнены и удалить комментарии.

- В блоке `catch` стоит заменить `RuntimeException` на более специфичное исключение времени выполнения (возможно, для этого и оставлен `TODO`).

Например так:

```java
public class DataAccessInitializationException extends RuntimeException {

    }
}


} catch (HibernateException e) {

}
```

- Класс не является `final` и имеет публичный конструктор. Это утилитный класс, и его экземпляры не должны существовать. ### AppContextListener

- ❗️`AppContextListener` не реализует метод `contextDestroyed`, который вызывается при остановке приложения.

В приложении есть ресурсы, которые требуют явного освобождения (например, `SessionFactory` в Hibernate, которая управляет пулом соединений). Без реализации `contextDestroyed` нет гарантированного способа их закрыть. Это приведёт к утечкам ресурсов, особенно в окружении сервера приложений, где приложение может многократно перезапускаться.

Как исправить: Реализовать метод `contextDestroyed` и вызывать в нём методы для освобождения всех ресурсов, созданных при старте.

```java
@Override
public void contextDestroyed(ServletContextEvent sce) {
    HibernateUtil.shutdown();
}
```

- При сохранении объектов в `ServletContext` в качестве ключей используются жёстко закодированные строки (`"matchesService"`, `"playerService"` и тд).

Вместо этого можно использовать в качестве ключа константу, которая не подвержена опечаткам, например, полное имя класса интерфейса.

```java
// При сохранении
```

## pom.xml

- ❗️Некоторые ключевые зависимости используют версии `alpha` или `milestone`.

```xml
<properties>
    <jakarta.servlet.version>6.2.0-M1</jakarta.servlet.version>
    <hibernate.version>8.0.0.Alpha1</hibernate.version>
    <slf4j.version>2.1.0-alpha1</slf4j.version>
    <junit.version>6.1.0-M1</junit.version>
</properties>
```

Alpha и milestone версии программного обеспечения являются предварительными выпусками. Они:

  - Нестабильны: Могут содержать большое количество ошибок, которые ещё не обнаружены и не исправлены.
  - Неполноценны: Могут иметь нереализованный функционал или неполный API.
  - Быстро меняются: API может измениться в любой момент без обратной совместимости.

Использование таких версий в проекте может приводить к непредсказуемому поведению, ошибкам и усложнить поддержку.

Как исправить: Использовать стабильные (GA - General Availability) версии зависимостей. Всегда стоит выбирать последнюю стабильную совместимую версию.

Например, такие:

```xml
<properties>
    <jakarta.servlet.version>6.1.0</jakarta.servlet.version>
    <hibernate.version>7.2.5.Final</hibernate.version>
    <slf4j.version>2.0.17</slf4j.version>
    <junit.version>6.0.3</junit.version>
</properties>
```

- В секции `<properties>` проекта указаны версии Java 22 для компилятора, но в конфигурации `maven-compiler-plugin` они переопределены на Java 21.

```xml
    <properties>
        <maven.compiler.source>22</maven.compiler.source>
        <maven.compiler.target>22</maven.compiler.target>
        <!-- ... -->
    </properties>
    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <configuration>
                    <source>21</source>
                    <target>21</target>
                </configuration>
            </plugin>
        </plugins>
    </build>
```

Указание разных версия создаёт путаницу и является источником потенциальных ошибок.

  - Неясно, какая версия Java на самом деле используется для компиляции.

  - Нет необходимости указывать версию компилятора в двух местах, если она должна быть одной и той же.

  - IDE может использовать информацию из `<properties>`, что приведёт к конфликту с настройками плагина.

Как исправить: Удалить настройки `source` и `target` из конфигурации `maven-compiler-plugin` и оставить их только в секции `<properties>`. Выбрать одну стабильную версию Java (например, 21).

- В плагине `maven-compiler-plugin` явно не указана его версия.

```xml
<plugins>
    <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-compiler-plugin</artifactId>
        <configuration>
            <!-- ... -->
        </configuration>
    </plugin>
</plugins>
```

Когда версия плагина не указана, Maven использует версию по умолчанию, определённую в своём Super POM (текущую версию можно посмотреть через команду `mvn help:effective-pom`, которая выведет в консоль объединённый POM).

Версия по умолчанию может измениться в новой версии Maven, что сломает сборку, которая раньше работала. Поэтому лучше всегда явно указывать версию используемого плагина.

Вот так:

```xml
<properties>
    <!-- ... -->
    <maven.compiler.plugin.version>3.15.0</maven.compiler.plugin.version>
</properties>

<plugins>
    <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-compiler-plugin</artifactId>
        <version>${maven.compiler.plugin.version}</version>
        <configuration>
            <!-- ... -->
        </configuration>
    </plugin>
</plugins>
```

- В `pom.xml` для плагина компиляции используются свойства `maven.compiler.source` и `maven.compiler.target`.

```xml
<properties>
    <maven.compiler.source>22</maven.compiler.source>
    <maven.compiler.target>22</maven.compiler.target>
    <!-- ... -->
</properties>
```

Начиная с Maven Compiler Plugin версии 3.6 и Java 9+, предпочтительнее использовать свойство `maven.compiler.release`.

Можно заменить `maven.compiler.source` и `maven.compiler.target` на `maven.compiler.release`.

```xml
<properties>
    <maven.compiler.release>22</maven.compiler.release>
    <!-- ... -->
</properties>
```

Это предотвратит ошибки совместимости, так как компилятор будет использовать только API, доступные в целевой версии Java.

Если в базе данных будет 100, 1000 или больше страниц с матчами, на странице будут отрисованы все 1000 ссылок. Это загромождает интерфейс, делая его непригодным для использования.

Стоит выбрать имя корневого пакета и переместить все существующие пакеты в него. Стандартное соглашение — перевёрнутое доменное имя (например, `ru.yourcompany.tennisscoreboard`). ### Использование `@Data` (Lombok) и `@Entity` (JPA) в одном классе <a id="data-entity"></a>

Аннотация `@Data` в Lombok — это удобный ярлык, который автоматически генерирует сразу несколько методов: `@Getter`, `@Setter`, `@RequiredArgsConstructor`, `@ToString` и `@EqualsAndHashCode`.

Применение `@Data` к JPA-сущности требует осторожности из-за автоматической генерации методов `equals()`, `hashCode()` и `toString()`, которые по умолчанию включают все поля класса.

<details>

<summary><b>Использование `@ToString` (Lombok) и `@Entity` (JPA) в одном классе</b></summary>

---

### @ToString и @Entity <a id="tostring-entity"></a>

При совместном использовании `@ToString` (Lombok) и `@Entity` (JPA) необходимо соблюдать определенные правила, чтобы избежать распространенных проблем с JPA и Hibernate.

Основная проблема заключается в том, что `@ToString` по умолчанию включает все поля класса в сгенерированный метод `toString()`. Это может привести к следующим трудностям при работе с JPA-сущностями:

- StackOverflowError: если сущности имеют двунаправленные связи (например, Parent ссылается на Child, а Child на Parent), вызов `toString()` на одном объекте приведет к бесконечной рекурсии вызовов `toString()` между связанными объектами, что быстро исчерпает стек вызовов.
- Проблема N+1 запросов и нежелательная загрузка ленивых коллекций (Lazy Loading Issues): если `@ToString` пытается получить доступ к полям с ленивой загрузкой (`FetchType.LAZY`), которые ещё не были загружены из базы данных в текущей сессии (например, при вызове `toString()` вне транзакции), это приведет к ошибке LazyInitializationException.

Чтобы безопасно использовать `@ToString` с JPA-сущностями, необходимо исключить поля отношений из генерации `toString()`:

с помощью аннотации над полем
```java
@ToString.Exclude
```

или в аннотации над классом (старый подход)
```java
@ToString(exclude = "childEntity")
```

или использовать над классом
```java
@ToString(onlyExplicitlyIncluded = true)
```
и явно указывать нужные поля через аннотацию надо полем
```java
@ToString.Include
```

### @EqualsAndHashCode и @Entity <a id="equalsandhashcode-entity"></a>

При совместном использовании @EqualsAndHashCode (Lombok) и @Entity (JPA/Hibernate) необходимо соблюдать определенные правила, чтобы избежать распространенных проблем, связанных с управлением персистентностью и прокси-объектами.
Основная проблема заключается в том, как JPA/Hibernate создает прокси-объекты (proxy) для ленивой загрузки (lazy loading) связанных сущностей. `@EqualsAndHashCode` по умолчанию генерирует методы `equals()` и `hashCode()`, которые используют все поля класса, включая поля отношений и, что критично, поле ID.
Это может привести к следующим трудностям:

- Проблемы с прокси-объектами Hibernate: Hibernate использует прокси (наследники класса сущности, определённого в проекте) для реализации ленивой загрузки. Если методы `equals()` и `hashCode()` напрямую обращаются к полям ID (до их инициализации) или полям отношений, это может нарушить работу механизма проксирования. Два прокси-объекта, представляющие одну и ту же сущность в базе данных, могут быть признаны неравными, если Lombok сгенерировал методы до того, как Hibernate инициализировал все необходимые поля.
- Неожиданное поведение в коллекциях (Set и Map): Сущности часто хранятся в коллекциях (Set или Map). Если `hashCode()` объекта меняется после его добавления в коллекцию (например, когда объекту присваивается ID после сохранения в БД), поиск и удаление этого объекта из коллекции работать не будет.

Рекомендуемый подход к реализации `equals()` и `hashCode()` для JPA-сущностей:

- Не использовать `@EqualsAndHashCode` по умолчанию — лучше написать эти методы вручную.
- Если всё же используется Lombok, надо исключить все поля отношений и не использовать поле id в вычислениях `equals()`/`hashCode()` до тех пор, пока объект не будет сохранен и ID будет гарантированно не равен null.

Чтобы безопасно использовать `@EqualsAndHashCode` с JPA-сущностями, необходимо исключить все поля отношений и явно указать, какие поля использовать, либо исключить все:

```java
@Entity
@EqualsAndHashCode(onlyExplicitlyIncluded = true) // Использовать только помеченные поля
public class ParentEntity {

    @Id
    @EqualsAndHashCode.Include // Явно включаем ID
    private Long id;

    // Все остальные поля и отношения исключены по умолчанию
    private String name;

    // @EqualsAndHashCode.Include здесь нет, поле игнорируется
    @OneToMany(mappedBy = "parent")
    private List<ChildEntity> children;
}

```

### Использование зарезервированных слов в качестве названий в БД <a id="sql-keywords"></a>

Использование зарезервированного слова (например, `USER`, `ORDER`, `GROUP`) в качестве названия таблицы в базе данных — это плохая практика, которая может привести к ряду проблем.

Вот основные из них:

### 1. Синтаксические ошибки

Это самая главная и частая проблема. SQL-парсер видит зарезервированное слово и ожидает определённой синтаксической конструкции, а не названия таблицы.

**Пример:**
При попытке получить все записи из таблицы с названием `ORDER`.
```sql
SELECT * FROM ORDER;
```
этот запрос, скорее всего, вызовет ошибку, потому что `ORDER` — это ключевое слово для `ORDER BY` (сортировка). Парсер будет ожидать после него `BY` и не поймёт, что `ORDER` — это название таблицы.

### 2. Необходимость экранирования (Quoting)

Чтобы обойти синтаксические ошибки, придётся постоянно заключать название таблицы в специальные кавычки, которые зависят от конкретной СУБД:

* **MySQL / MariaDB:** обратные кавычки (`` ` ``)
    ```sql
    SELECT * FROM `ORDER`;
    ```
* **PostgreSQL / Стандарт SQL:** двойные кавычки (`" "`)
    ```sql
    SELECT * FROM "ORDER";
    ```
* **SQL Server:** квадратные скобки (`[ ]`)
    ```sql
    SELECT * FROM [ORDER];
    ```

### 3. Снижение читаемости и усложнение кода

Из-за необходимости постоянного экранирования код становится менее читаемым. Разработчики могут легко забыть поставить кавычки, что приведёт к ошибкам, на поиск которых уйдёт время.

### 4. Проблемы с ORM и другими инструментами

Инструменты, которые автоматически генерируют SQL-запросы (например, Hibernate, JPA, SQLAlchemy и другие ORM), а также различные GUI-клиенты и утилиты для миграции, могут не справиться с такими названиями. Они могут не знать, что `ORDER` нужно экранировать, и будут генерировать нерабочий SQL-код. Это потребует дополнительной конфигурации или ручного вмешательства.

### 5. Потеря переносимости

Ключевые слова могут отличаться в разных СУБД. Слово, которое не зарезервировано в одной системе, может быть зарезервировано в другой. Если команда сменит СУБД, проект с такими названиями таблиц потребует значительной доработки.

---

**Лучшая практика:**

**Никогда не использовать зарезервированные слова для названий таблиц, столбцов и других объектов в БД.**

Всегда проверять список зарезервированных слов для основных СУБД. Чтобы избежать случайных совпадений, можно придерживаться соглашений об именовании, например:
* Использовать префиксы: `tbl_order`.
* Использовать множественное число (если слово во множественном числе не зарезервировано): `orders` (слово `orders` не зарезервировано).
* Добавлять суффиксы: `order_data`.

### Принцип наименьшего удивления (Principle of Least Astonishment, POLA) <a id="pola"></a>

**Система должна вести себя так, как от неё ожидает большинство пользователей (разработчиков), и не должна вызывать удивление или замешательство.**

Это означает, что API, класс, метод или даже однострочное выражение должны быть **интуитивно понятными** и **предсказуемыми** для другого разработчика.

### Ключевые аспекты принципа

- Следование общепринятым соглашениям и идиомам: Имена методов и классов должны точно отражать их поведение. Геттеры начинаются с `get`/`is`, сеттеры — с `set`. Классы — `CamelCase`, переменные — `camelCase`, константы — `UPPER_SNAKE_CASE`.

- Предсказуемость поведения: Поведение методов должно быть интуитивно понятным и соответствовать тому, что подразумевает их имя и сигнатура.

- Соблюдение контрактов методов:

    - Если метод называется `getSomething()`, он должен возвращать что-то, а не изменять состояние.

    - Если метод называется `calculateSomething(params)`, он должен вычислять и возвращать результат, а не изменять переданные параметры.

- Следование единому стилю: Если в одном методе используется порядок параметров `(source, destination)`, то его следует придерживаться во всех похожих методах. Нельзя в другом методе делать `(destination, source)`.

- Согласованные возвращаемые значения: Если семейство методов возвращает `-1` при ошибке, не стоит в одном из них возвращать `0` или бросать исключение без веской причины.

Принцип наименьшего удивления в программировании — это о снижении когнитивной нагрузки на других разработчиков. Это создание кода, который ведёт себя так, как от него ждут, потому что он следует установленным правилам, здравому смыслу и согласованности. Следование этому принципу напрямую ведёт к созданию более чистого, поддерживаемого и надёжного кода.

### Принцип Single Source of Truth (SSOT) <a id="ssot-principle"></a>

Принцип Single Source of Truth (SSOT), или "Единый источник истины", в контексте программирования и управления данными означает архитектурный подход, при котором все данные о конкретной сущности или состоянии системы хранятся и управляются в одном единственном, авторитетном месте.

Суть принципа заключается в том, чтобы избежать дублирования информации и обеспечить ее согласованность. Если данные существуют в нескольких местах, всегда есть риск их расхождения, что приводит к ошибкам, путанице и неверным решениям.

#### Преимущества:

- Согласованность данных: невозможно иметь противоречивое состояние.
- Упрощение отладки и поддержки: данные берутся и изменяются только в одном месте.
- Упрощение тестирования: легче тестировать, так как состояние определяется одним источником.
- Повышение надежности: уменьшает количество ошибок и повышает уверенность в точности информации.

#### Возможные недостатки:
- Производительность: постоянное вычисление может быть дороже, чем хранение поля.
- Сложность вычислений: иногда вычисление сложное.

Следование принципу SSOT делает код более предсказуемым, надёжным и понятным.

### Принцип разделения ответственности (Separation of Concerns) в архитектуре MVC(S) <a id="soc-principle"></a>

## Введение

Любое программное приложение со временем усложняется. Чтобы сохранить возможность развивать и поддерживать его, в разработке используют принцип **разделения ответственности (Separation of Concerns, SoC)**. Суть его такая: каждый модуль или слой системы должен отвечать за одну чётко определённую задачу. Это улучшает читаемость кода, упрощает тестирование, позволяет заменять отдельные части без влияния на остальные.

## Общая архитектура MVC(S)

MVC (Model-View-Controller) – архитектурный паттерн для разделения данных приложения и управляющей логики на три отдельных компонента: модель, представление и контроллер. В веб-приложениях его часто расширяют до **MVC(S)**, где отдельно выделяют слой **Service** (бизнес-логика).

- **View (Представление)** – то, что видит пользователь (JSP-страницы).
- **Controller (Контроллер)** – сервлеты, которые принимают HTTP-запросы, вызывают нужные сервисы и передают данные в представление.
- **Model (Модель)** – данные и логика их обработки. В текущем проекте модель состоит из нескольких подуровней:
    - **Domain Model (Доменная модель)** – объекты, отражающие бизнес-сущности и правила.
    - **Service (Сервис)** – слой, содержащий бизнес-логику и координирующий работу с данными.
    - **DAO (Data Access Object)** – объекты доступа к данным, работающие с JPA-сущностями.
    - **JPA-Entity** – сущности, привязанные к таблицам базы данных через JPA-аннотации.
    - **DTO (Data Transfer Object)** – объекты для передачи данных между слоями (например, между сервисом и контроллером).

Такое расслоение позволяет чётко разграничить зоны ответственности каждого компонента.

## Детальный разбор слоёв

### 1. JSP (View)

JSP отвечает только за **отображение данных**, полученных от контроллера, и за формирование HTML-форм для отправки данных на сервер. JSP не должна содержать бизнес-логики, обращений к базе данных или прямых вызовов сервисов. Все необходимые для рендеринга данные контроллер помещает в атрибуты запроса (или сессии).

### 2. Сервлеты (Controller)

Сервлет выступает в роли **контроллера** – точки входа для HTTP-запросов. Его обязанности:
- Прочитать параметры запроса.
- Вызвать соответствующий метод сервиса (передав при необходимости DTO или простые параметры).
- Обработать результат: поместить данные в атрибуты запроса/сессии.
- Выбрать представление (JSP) для ответа и выполнить перенаправление или forward.

Контроллер **не должен содержать** бизнес-логику и код доступа к данным. Всё это делегируется сервисам.

### 3. DTO (Data Transfer Object)

DTO – это простые объекты, которые служат только для **передачи данных** между слоями приложения. Они не содержат бизнес-логики и обычно имеют только поля, конструкторы и геттеры/сеттеры.

Зачем нужны DTO, если есть доменные модели и JPA-сущности? Причины:
- **Изоляция представления от модели данных.** JSP может использовать только те поля, которые действительно нужны на странице, и не видеть, например, методы доменных объектов.
- **Упрощение сериализации.** Если понадобится отдавать данные в формате JSON, DTO удобно преобразовывать в JSON без риска зацикливания (при связях между сущностями).
- **Безопасность.** Нельзя случайно передать на клиент пароль или внутренние флаги.

### 4. Сервисы (Service)

Сервисный слой содержит **бизнес-логику приложения**. Здесь выполняются:
- Проверки правильности данных (валидация, которая не может быть выполнена на уровне БД).
- Координация нескольких DAO (например, перевод денег со счёта на счёт).
- Вычисления, формирование отчётов, отправка уведомлений.
- Преобразование доменных объектов в DTO (и обратно).

Сервис ничего не знает о том, как данные будут отображаться (JSP, REST и т.д.) и откуда пришёл запрос. Он работает с доменными моделями и DAO.

### 5. Доменные модели (Domain Model)

Доменная модель представляет **бизнес-сущности** и правила. В простейшем случае это могут быть POJO-классы, похожие на JPA-сущности, но с дополнительными бизнес-методами. В идеале доменная модель не зависит от способа хранения (БД) и содержит поведение.

### 6. JPA-Entity

Это класс, помеченный аннотациями JPA (@Entity, @Table и т.д.), который **отображается на таблицу базы данных**. Его поля соответствуют колонкам. Он может содержать аннотации связей (@OneToMany, @ManyToOne).

### 7. DAO (Data Access Object)

Слой DAO отвечает исключительно за **доступ к данным**. Он использует JPA EntityManager для выполнения CRUD-операций и запросов. DAO не должен содержать бизнес-логику. В простейшем случае методы: findById, findAll, save, update, delete.

## Принципы взаимодействия слоёв

Чтобы разделение ответственности работало, нужно строго соблюдать правила взаимодействия между слоями. Вот основные принципы:

1. **Контроллер** общается только с **сервисом**. Он передаёт ему данные из запроса (возможно, упакованные в DTO) и получает от сервиса DTO или простые типы.
2. **Сервис** работает с **DAO** и **доменными моделями**. Он может преобразовывать доменные объекты в DTO и обратно, но не должен знать о существовании HTTP-сессии или JSP.
3. **DAO** работает только с **JPA-сущностями** и EntityManager. Он не содержит бизнес-логики.
4. **JSP** использует только те данные, которые передал контроллер (атрибуты запроса). Никаких обращений к сервисам или DAO из JSP быть не должно.
5. **DTO** используются для передачи данных между **сервисом и контроллером** (или контроллером и представлением). Они не должны содержать ссылок на EntityManager или зависеть от JPA.

Такая изоляция позволяет менять реализацию любого слоя без влияния на другие. Например, можно заменить JSP на другой движок представлений (например, Thymeleaf), заменив только контроллер и добавив новые шаблоны. Или заменить Hibernate на другую реализацию JPA, изменив только DAO.

## Преимущества разделения ответственности

Когда каждый класс выполняет строго свою функцию, это даёт ряд преимуществ:

- **Лёгкость поддержки и модификации**. Если нужно изменить способ отображения (например, добавить пагинацию), меняется только JSP и, возможно, контроллер. Бизнес-логика остаётся нетронутой.
- **Тестируемость**. Сервисы можно тестировать с мок-объектами DAO без запуска сервера. DAO можно тестировать с in-memory БД (например, H2).
- **Возможность замены технологий**. Если нужно заменить JSP на Freemarker, понадобится новый контроллер (или модификация существующего), но сервисы и DAO не меняются. Чтобы перейти с Hibernate на EclipseLink меняется только JPA-провайдер и, возможно, настройки – код DAO остаётся тем же (если используется стандартный JPA API).
- **Командная разработка**. Разные разработчики могут параллельно работать над представлением, бизнес-логикой и доступом к данным, если чётко определены интерфейсы взаимодействия.

## Заключение

Разделение ответственности – фундаментальный принцип, который стоит применять даже в небольших проектах, чтобы избежать "каши" из кода и облегчить дальнейшее развитие.

Такой подход готовит почву для перехода на более мощные фреймворки (например, Spring), которые предлагают готовые механизмы для реализации этих слоёв (например, Spring MVC, Spring Data, Spring Web Services). Но даже без фреймворков, при следовании принципам SoC, получается чистый, понятный и гибкий код.

Главная цель разделения ответственности – упростить жизнь разработчикам и обеспечить долгосрочную жизнеспособность приложения.

### Анемичная vs Богатая модель предметной области <a id="reach-anemic-model"></a>

> **Богатая модель** инкапсулирует как данные (состояние), так и всю связанную с ними бизнес-логику и поведение внутри классов предметной области, обеспечивая высокий уровень инкапсуляции.
>
> **Анемичная модель**, напротив, содержит только свойства (данные), а логика обработки этих данных вынесена в другие компоненты (как правило, сервисы).
>
> **Богатая модель (Rich Domain Model / Fat Model):**
> - Интегрирует данные и бизнес-логику в единое целое (в классах сущностей).
> - Объекты являются полноценными и самодостаточными, отвечают за собственную консистентность и поведение.
> - Соответствует ключевой идее объектно-ориентированного программирования — инкапсуляции.
> - Основа Domain-Driven Design (DDD) и чистой архитектуры.
>
> **Анемичная модель (Anemic Model):**
> - Хранит только состояние (свойства/поля).
> - Поведение (методы с бизнес-логикой) отсутствует или сведено к минимуму (сеттеры/геттеры).
> - Классы больше напоминают структуры данных (DTO) или записи (record), а не полноценные объекты.
> - Часто приводит к "Сервисному спагетти-коду" (Service Layer Spaghetti), когда сервисы разрастаются, управляя данными извне.

### Архитектурный антипаттерн: "Толстый контроллер" (Fat Controller) <a id="fat-controller"></a>

"Толстый контроллер" — это распространенный антипаттерн в приложениях, построенных на архитектуре MVC (Model-View-Controller). Он возникает, когда слой контроллеров берет на себя слишком много ответственности. Вместо того чтобы быть тонким связующим звеном, он разрастается и вбирает в себя логику, которая должна находиться в других слоях приложения.

#### Как должно быть

В идеальной архитектуре **"Худые контроллеры, толстые модели" (Thin Controllers, Fat Models)**, обязанности строго разделены:

| Слой  | Обязанности |
|:---|:---|
| **Худой Контроллер** (Thin Controller) | - Принять HTTP-запрос и разобрать его параметры.<br>- Вызвать **один** метод в сервисном слое (модели), передав ему эти данные.<br>- Получить от сервиса результат. <br>- Выбрать подходящее представление (View) и передать ему результат для отображения. |
| **Толстая Модель (Сервисный слой)** (Fat Model) | - Бизнес-логика: Сложные вычисления, принятие решений, изменение состояния бизнес-сущностей.<br>- Логика доступа к данным: Прямые запросы к базе данных (например, через DAO или EntityManager).<br>- Оркестрация: Координация работы нескольких сервисов для выполнения одной бизнес-операции.<br>- Управление транзакциями.|

При таком подходе бизнес-логика становится независимой от веб-слоя, легко тестируется и может быть переиспользована где угодно.

"Толстый контроллер" нарушает это разделение. Он начинает содержать в себе бизнес-логику, логику доступа к данным, оркестрацию нескольких сервисов и даже форматирование данных.

#### Последствия "Толстого контроллера"

1. Нарушение Принципа единственной ответственности (SRP): Контроллер начинает делать всё сразу, что делает код запутанным и сложным для понимания.

2. **Низкая тестируемость:** Бизнес-логику внутри контроллера практически невозможно протестировать в изоляции от веб-контекста.

3. **Плохая переиспользуемость:** Логика, "запертая" в контроллере, не может быть повторно использована в других частях системы (например, в фоновых задачах или для мобильного API).

4. **Дублирование кода (нарушение DRY):** Если похожая бизнес-операция понадобится в другом контроллере, высока вероятность, что разработчик просто скопирует кусок кода, вместо того чтобы вынести его в общий сервис.

5. **Сложность в поддержке:** Код становится запутанным, а его обязанности — размытыми, что усложняет отладку и внесение изменений.

#### Решение

Решение заключается в рефакторинге: необходимо переносить всю бизнес-логику и логику оркестрации из контроллеров в соответствующий **сервисный слой**. Контроллер должен оставаться "худым" — его единственная задача быть посредником между миром HTTP и приложением.
